# 测试设计方法选择规则

本规则库回答一个问题：**面对一条需求，该用哪种测试设计方法，以及用完之后应该产出什么样的用例。**
不要为了「看起来专业」而堆方法——每种方法都对应一类缺陷的发现能力，选错等于这类缺陷测不到。

---

## 一、方法选择决策表

| 需求特征（在 PRD 里的信号） | 主方法 | 补充方法 | 该类需求漏测的典型后果 |
|---|---|---|---|
| 输入有明确取值范围 / 长度 / 格式（「1-100」「不超过 30 位」「手机号」「必填」） | 等价类划分 | 边界值分析 | 只测了一个合法值，非法输入直接穿透到数据库或下游 |
| 有离散条件组合（「当 A 且 B 时…否则…」「按角色区分」「满足任一条件」） | 判定表 | 等价类划分 | 组合分支漏测，条件叠加时的兜底逻辑从没被执行过 |
| 有状态与流转（草稿→待审→已审→归档；锁定/解锁；订单状态机） | 状态迁移 | 场景法 | 非法跳转未被拦截；终态还能被改 |
| 跨页面 / 跨模块的完整业务流（「从下单到兑付」「端到端」） | 场景法 | 状态迁移 | 单点都测过，串起来走不通；中间态数据不一致 |
| 多参数配置组合且组合数爆炸（机型 / 浏览器 / 参数矩阵） | 正交实验 | 等价类划分 | 全组合测不完于是随便挑几个；某个配对上线才炸 |
| 接口契约（入参出参、错误码、幂等、超时、并发） | 等价类划分 + 边界值 | 场景法（异常流） | 错误码与重试语义没人验；并发重复写入 |
| 性能 / 容量 / 时延指标（「≤2 秒」「支持 500 并发」） | 场景法（负载场景） | 边界值（阈值附近） | 指标写进文档但从没被量过 |
| 权限 / 数据可见性 / 敏感信息 | 判定表（角色 × 操作） | 场景法（越权尝试） | 只测了有权角色；越权请求返回 200 |
| 纯展示与交互（文案、控件状态、空态、加载态） | 等价类划分（数据形态） | 场景法 | 空数据 / 超长数据把布局撑破，没人看过 |

判据不显著时（「既是接口又是状态流」），**两种都要用**，但要在 notes 里说明为什么这条需求需要两类用例，避免用例集无意义膨胀。

---

## 二、等价类划分

**做法**：把输入域切成若干「处理上等价」的类，每类只取一个代表值。必须同时列出**有效类**与**无效类**——只列有效类等于没做。

**产出形态**：每个有效类 1 条 + 每个关键无效类 1 条；无效类用例的预期结果重点在**拦截与提示**，不是崩溃。

示例（需求：「金额输入框，范围 0.01–1,000,000.00，最多 2 位小数」）：

| 等价类 | 代表值 | 用例意图 |
|---|---|---|
| 有效-最小合法 | `0.01` | 正常受理 |
| 有效-常规 | `1,000.00` | 正常受理 |
| 有效-最大合法 | `1000000.00` | 正常受理 |
| 无效-零金额 | `0` | 提示「金额必须大于 0」，不落库 |
| 无效-负数 | `-100` | 输入被拦截或提示，不出现负向记账 |
| 无效-超上限 | `1000000.01` | 上限提示 |
| 无效-精度超限 | `1.234` | 截断或提示，规则需与 PRD 一致 |
| 无效-非数字 | `abc` | 输入框不接受 |

⚠️ 常见错误：把「有效类」写成一条大杂烩用例跑三个值。**一条用例只验一个等价类**，否则失败时定位不到是哪一类出的问题。

---

## 三、边界值分析

**做法**：在每个等价类的**边界上**取 `min-1 / min / min+1 / max-1 / max / max+1`（离散值）或「刚好等于 / 差一个」。数量规则与长度规则同样有边界。

**与等价类的关系**：等价类告诉你「取哪些代表值」，边界值告诉你「代表值应该贴着哪儿取」。两者是配套关系，不是二选一。

示例（承接上面的金额需求，边界集）：`0` / `0.01` / `0.02` / `999999.99` / `1000000.00` / `1000000.01`。

易漏边界（务必逐条排查是否适用）：

- **空值与空白串**：未填写、只填空格、粘贴只含空格；
- **长度边界**：字段最大长度 ±1（尤其会影响布局或索引的字段）；
- **数量边界**：分页末页只有 1 条 / 恰好满页；列表 0 条、1 条、超多条；
- **时间边界**：跨日 23:59:59→00:00:00、月末、闰年 2/29、时区切换、开始=结束；
- **阈值触发点**：「连续 5 次锁定」的第 4 次（不锁）与第 5 次（锁）、失败后成功一次是否清零；
- **并发/重复**：同一请求提交两次（幂等）、双击按钮、超时后重发。

## 四、判定表

**做法**：列出条件（C）与动作（A），把所有条件组合铺成列，去掉「条件取值不影响动作」的冗余列（用 `X` 标记忽略位），剩下的每一列至少一条用例。

**何时必须用**：出现「且 / 或 / 否则 / 除…之外 / 满足任一」这类措辞，或动作由 ≥2 个条件共同决定时。**两个条件就要铺 4 列**——靠脑补最容易漏的是「都为假」那一列。

示例（需求：「仅当账号已实名且未冻结且风险评分 <60 时免验证，否则需二次验证」）：

| 条件 | R1 | R2 | R3 | R4 | R5 |
|---|---|---|---|---|---|
| 已实名 | Y | Y | Y | Y | N |
| 未冻结 | Y | Y | N | X | X |
| 风险 <60 | Y | N | X | X | X |
| **动作：免验证** | ✓ | ✗ | ✗ | ✗ | ✗ |
| **动作：二次验证** | ✗ | ✓ | ✓ | ✓ | ✓ |

规则列数 ≤8 时可全组合；>8 时按「每个条件的真值至少被覆盖一次 + 关键风险组合」裁剪，并在 notes 说明裁剪依据（不要不声不响地少测）。

## 五、状态迁移

**做法**：先列状态集合与允许的迁移（`状态A --触发条件--> 状态B`），然后产出三类用例：

1. **合法迁移**：每条允许的迁移 1 条（从起点到终点的动作与该状态下的可见结果都要写清）；
2. **非法迁移**：对每个状态，列出**它不允许的操作**，至少对高风险项各出 1 条（预期是「拒绝 + 明确提示 + 状态不变」，不是报错页）；
3. **终态保护**：终态（已归档 / 已结清 / 已完成）上的写操作必须全部被拒。

必须额外验的两点：**状态变更后的数据一致性**（关联表/缓存/下游是否同步）与**并发迁移**（两个人同时操作同一对象，只能有一个成功）。

示例（需求：「待审 → 已审 → 归档；仅待审可编辑与删除」）：

| 用例意图 | 预期结果写法 |
|---|---|
| 待审提交审核成功 | 状态变为「已审」，操作记录新增一条含审核人与时间戳 |
| 已审状态下编辑 | 编辑入口不可用；直接调接口返回「当前状态不允许编辑」，状态仍为「已审」 |
| 归档后删除 | 拒绝，状态仍为「已归档」，列表不再显示该记录（按归档筛选可见） |
| 两人同时审核同一记录 | 仅一人成功，另一人收到「状态已变更」提示，不产生两条审核记录 |

## 六、场景法（业务流程法）

**做法**：以**业务事件流**为单位组织用例——主成功场景（基本流）1 条 + 每个备选/异常流各 1 条以上。步骤跨页面、跨模块，重点是**流转过程中数据在持续正确**。

**与前面方法的区别**：等价类/边界值/判定表/状态迁移测「点」，场景法测「线」。只有点没有线 → 上线后跑不通主流程；只有线没有点 → 分支异常没人管。

**基本流产出要求**：端到端每一步都要给该步预期，并显式覆盖三条：
① 起点前置条件（谁、什么状态下进入）；② 关键中间态（生成/变更的单据编号、状态、金额）；③ 终点可核对物（列表出现该记录、统计数字变化、通知送达）。

**异常流清单**（逐条判断是否适用）：中途退出/返回、超时、网络失败、并发冲突、审批驳回回退、部分失败（批量中第 N 条失败）、重复提交、撤销/冲正。

## 七、正交实验

**做法**：因素（F）与水平（L）建表，用正交表挑最少的组合，保证「任意两个因素的水平组合至少各出现一次」。

**适用信号**：参数组合数 = 各因素水平数相乘且 >12（>12 组合明显测不完）。
**不适用**：只有 2-3 个因素（直接全组合更省事）；因素之间互斥或存在依赖（先按判定表处理依赖关系，再对剩余正交）。

**产出要求**：写清用了哪张正交表、覆盖多少组合、被排除的组合（互斥约束）与理由。水平选取要贴风险：把「最容易出问题的水平」放进来，而不是每一因素都取第一个水平。

---

## 八、方法用完后仍必须补的三类

设计方法负责「有逻辑地覆盖」，但下列三类不属于任何方法的产出，**必须单独补**，否则是常见事故源：

1. **数据一致性**：同一数据在列表页 / 详情页 / 统计 / 导出 / 检索结果中的呈现是否一致（新增后统计 +1、导出内容与界面同值）；
2. **边界之外的「没有数据」**：空态、无权限态、加载失败态——PRD 没写就是缺陷吗？不是，PRD 没写要在 notes 提出来；
3. **回归锚点**：本次改动可能波及的既有主流程，各留 1 条 `type: regression` 或 `smoke` 用例（给未来的改动兜底）。
