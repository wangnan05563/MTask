# 用例书写规范（标题 / 步骤 / 可判定预期 / 禁用表述）

本规则库决定用例**读起来能不能直接用**。同样的测试意图，写法不合格就是废用例：执行的人要靠猜，判定的时候吵不出结论。

一句话标准：**预期结果必须能让两个人各自独立执行同一条用例，并得出相同的是/否结论。**

---

## 一、标题

**公式**：`[对象/条件] + [动作] + [可判定的结果]`（取其中能唯一定位的两到三段即可，不必硬塞）

- 长度 ≤ 40 字；同一需求内不重复；不带标点结尾。
- 必须能看出**测的是哪条规则**，不能只看出模块。
- 不写编号、不写「测试」「验证」「检查」「用例」这类起手词（都是零信息量）。

| ✗ 不合格 | 为什么 | ✓ 合格 |
|---|---|---|
| 测试登录功能 | 无对象条件无结果，等于没标题 | 使用已注册手机号与正确密码登录成功 |
| 密码校验 | 看不出测哪条规则 | 密码错误时提示「账号或密码错误」且不跳转 |
| 边界值测试 | 看不出边界在哪 | 金额输入 1000000.01 时提示超出上限且不提交 |
| 正常下单流程（补充） | 括号噪声 + 无结果 | 提交订单后生成待审核单据并出现在列表首行 |
| 列表分页 | 一条标题覆盖不了多条判定 | 第 2 页显示第 201-400 条记录且「下一页」可点击 |

---

## 二、前置条件（`preconditions`）

写**执行前必须成立的状态**，不写操作步骤（那是 steps 的事）。

- ✓ 具体状态：「用户已完成注册且账号未锁定」「存在一张状态为『待审』的单据，当前登录人是审核人」
- ✗ 空话：「环境正常」「数据已准备」「用户已登录」（若确实要登录，写清以什么身份登录）
- 需要特定角色/数据时**在前置条件里点名**，不要假装执行者知道。
- 若用例本身包含「登录」这一步，就别再把它写进前置条件（重复会导致执行歧义）。

---

## 三、步骤（`steps[]`）

一条步骤 = **一个动作**。`action` 写「做什么」，`expected` 写「做完立刻能看到什么」。

`action` 规则：

1. 以**可执行动词**开头（打开 / 输入 / 点击 / 提交 / 调用 / 切换 / 勾选 / 等待），不要写「看看」「确认」（那是判定，属于 expected）。
2. 带上**操作对象与数据**：「输入手机号 `13800000000` 与密码 `Pass@123`」，不是「输入账号密码」。
3. 不合并动作：「输入并提交」是两步——出错时无法判断是输入环节还是提交环节。
4. 接口类用例写清**方法 + 路径 + 关键参数**（如「以他人单据 id 调用 `POST /api/xxx/{id}/audit`，当前登录人无权限」）。
5. 步骤数建议 2-8 步；超过 8 步说明这条用例在做两件事，应拆分。

`expected`（该步预期）规则：

- 只写**这一步之后立刻可观测**的结果，别把最终结果提前写。
- 界面类：写出可见元素/文案/数值/状态（「列表首行出现刚提交的单据，状态列为『待审』」）。
- 接口类：写出状态码 + 响应关键字段 + 副作用（「返回 400，`error` 含『无权审核』；该单据状态保持『待审』」）。
- 该步确实无可观测变化（如只是等待）时，`expected` 可写「页面无变化」这类**可核对**描述，不要留空字符串。

---

## 四、预期结果必须「可判定」

可判定的三要素，缺一个就退回重写：

| 要素 | 说明 | 例子 |
|---|---|---|
| **在哪看** | 定位到具体界面位置 / 字段 / 接口响应 / 数据表 | 「订单详情页的『实付金额』字段」 |
| **看到什么** | 具体文案、数值、状态、数量、顺序 | 「显示『实付金额：¥1,000.00』」 |
| **不该看到什么** | 负向与拦截类必写 | 「不生成新订单记录，`orders` 表行数不变」 |

数值能给就给准（金额、条数、时长、状态名）；PRD 没给准的**不要编一个**——写「按 PRD 3.2 规则计算的金额」并在 notes 记一条「金额计算规则未明确」。

---

## 五、禁用模糊表述（输出前逐词扫一遍）

判定口径：下表词语**作为唯一的判定内容**出现时不合格——写在「登录成功并跳转首页」里的「成功」有后面的可核对物托底，可以用；
只写「登录成功」不能用。区别就在于**能不能据此判出通过/失败**，而不是字面命中。

| 禁用 | 问题 | 改写方向 |
|---|---|---|
| 正常 / 正确 / `无误` | 没有定义什么叫正常 | 写出正确的具体形态（值、文案、状态） |
| 成功 | 不可观测 | 成功的可核对标志（跳转 + 记录 + 数量变化） |
| `符合要求` / `符合预期` | 循环论证 | 直接把要求复述成可核对条件 |
| 合理 / 适当 / 应该 | 主观 | 给出阈值或具体规则 |
| `无明显异常` / `无报错` | 「无异常」验不出缺陷 | 写清应出现的界面状态 + 不应出现的错误提示内容 |
| `显示友好提示` | 不知道提示长什么样 | 写出提示文案原文（PRD 有就给原文） |
| `系统不崩溃` / `不卡顿` | 无法判定 | 崩溃换「进程存活 + 接口 200」；慢换「≤2 秒内完成渲染」 |
| 可以 / 能够 / 支持 | 能力陈述不是判定 | 改成具体结果 |
| `数据库更新` | 没说更新成什么 | 写明表、字段、目标值（或行数变化） |
| `待补充` / `待定` / 略 | 空判 | 删除该用例或补全，不得留占位 |

表里**带反引号**的词是机检名单：任何语境下都零信息，字面命中即不合格（`server/scripts/skill-contract-check.mjs`
直接从本节抽取该名单，并用它扫《输出协议》里的示例）。
**不带反引号**的词（正常 / 正确 / 成功 / 应该 / 支持 / 略…）要看语境：作为唯一判定内容时不合格，
写在「登录成功并跳转首页」这类带可核对物的句子里可以用——这一部分机检故意不管，误伤「正确密码」「执行策略」这种正常表述比漏检更坑。

---

## 六、测试数据（`testData`）

- 给**具体值**或**明确的数据构造规则**，二者择一：「手机号 `13800000000` / 密码 `Pass@123`」「金额 `1000000.01`（上限 +0.01）」「构造 201 条记录，其中 3 条状态为『已归档』」。
- 多字段用 ` / ` 分隔，便于复制到执行环境。
- **禁止真实凭据与生产数据**：不写真实手机号/身份证/银行卡/口令/密钥/token；用示例值（`13800000000`、`Pass@123`、`999999`）。
- 需要敏感数据时用占位并说明规则：「使用测试环境已存在的一张金额 ≥ 100 万的票据号」。
- 边界类数据的**意图要写在标题或 expected 里**，只把数字塞进 testData 没人知道为什么是 `1000000.01`。

---

## 七、后置条件与清理（`postconditions`）

- 写了会创建 / 修改数据的用例，就要写清理动作：「删除本用例创建的测试单据」「退出登录并清理会话」「把金额恢复为初始值」。
- 只读类用例可留空字符串（不要写「无」，也不要用 `N/A` 占位堆字段）。

---

## 八、模块（`module`）与标签（`tags`）

- `module` 用 PRD 章节名或工作空间里**已存在**的模块/页面名，同一模块全批写法统一（不要一处「登录」、一处「登录模块」、一处「用户认证」）。
- 不要新造同义模块名——模块是筛选与导出的分组依据，散一次就永久脏。
- `tags`：逗号分隔，最多 3 个，用于横切分组（`冒烟` / `回归` / `需数据准备` / `依赖外部系统`）。不写优先级、不写模块名（那是 `module` 的事）。

---

## 九、格式与字符约束（直接影响能否被解析）

1. 所有字段值为**单行字符串**，不要出现换行符（要分点就拆成多条步骤）。
2. 字符串内的双引号必须转义；中文引号 `「」『』` 无需转义，可放心用于提示文案。
3. 字段值里**禁止出现** `<<<` / `>>>` 序列（会被当成协议标记切开）。
4. 长度参考：`title` ≤40 字、`action` ≤80 字、单步 `expected` ≤120 字、`preconditions`/`postconditions` ≤200 字。
   超限通常说明这条用例在干两件事——拆开比压缩措辞更好。
5. 不使用 Markdown 语法（**加粗**、`#`、表格）；不写代码围栏；不要在 JSON 里加注释或尾逗号。
6. 简体中文（枚举值、字段名、接口路径、英文错误码保持原样）。

---

## 十、输出前自检清单（每条用例逐项过）

1. 标题能否看出「哪条规则 + 什么结果」，且不重复；
2. `reqNo` 是否命中需求清单；
3. 每个 `action` 是否只有一个动作、带对象与数据；
4. 每个 `expected` 是否满足「在哪看 + 看到什么（+ 不该看到什么）」；
5. 有没有第五节的禁用词残留；
6. `testData` 是不是具体值/明确规则，且不含真实凭据；
7. 创建了数据的用例是否有清理；
8. 用例整体是否值得存在——如果它只是另一条的轻微变体且验不出新缺陷，删掉它比留着好看更重要。
