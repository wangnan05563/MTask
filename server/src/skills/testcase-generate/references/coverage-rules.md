# 需求覆盖与优先级分配规则

本规则库回答三个问题：**覆盖率的口径是什么、每条需求该出几条用例、优先级怎么定。**
所有判定必须与系统实现同口径，否则「AI 说 100% 覆盖」与「界面显示 18/22」会当场打架。

---

## 一、覆盖率口径（与系统实现严格一致）

- **分母 = 需求跟踪矩阵的条目数**（`prd_requirements` 中该项目的需求行），**不是** PRD 字数、不是模块数、不是用例数。
- **分子 = 至少有 1 条用例关联的需求数**。关联靠 `case.reqNo → requirement.reqNo` 映射，服务端写 `test_cases.req_id`。
- 系统口径来源：`GET /api/plans/test-cases/coverage` 返回 `{ total, covered, uncovered, rate, byReq[] }`，其中
  `total` 是**需求数**，`byReq` **刻意保留 `caseCount = 0` 的需求行**（就是为了让缺口看得见）。
- 因此：一条用例挂 5 个需求 ≠ 5 条用例。用例与需求是**多对一**——一条用例只挂一条需求；要覆盖多个需求就写多条用例。

### 强约束

1. 本次分块范围内**每条需求至少 1 条用例**（0 条就是缺口，会被 `byReq.caseCount=0` 点名）。
2. `reqNo` 悬空（既不在本次 `requirements` 也不在已有需求清单）→ 该用例会被丢弃或落为孤儿，
   **等于白写**。输出前逐条核对 `reqNo`。
3. 不要因为「这条需求不好测」而不输出——测不了就输出 1 条标注清楚（`expected` 写明待确认），并在 notes 点名。
   **静默丢需求是最坏行为**：草稿视图会显示未覆盖，用户会以为是生成器漏了。
4. 覆盖率不足时**不得**用增加低价值用例来凑数（同一需求堆 8 条同质用例，覆盖率不变，成本翻倍）。

---

## 二、每条需求出几条用例

以生成偏好的「默认每需求用例数」为基准（默认 **3**），在此之上按下表**加**，不要无差别铺：

| 需求特征 | 最低条数 | 组成要求 |
|---|---|---|
| 普通功能（单一规则） | 3 | 1 正向主路径 + 1 负向（非法输入/失败分支）+ 1 边界或空态 |
| 含输入校验（范围/长度/格式） | 4 | 正向 1 + 无效类等价类逐类 1 + 边界 ±1 + 空值 |
| 含条件组合（判定表） | 判定表规则列数 | 每条规则列 1 条，禁止把多列合进一条 |
| 含状态流转 | 合法迁移数 + 高风险非法迁移数 | 合法迁移逐条 + 终态保护 + 并发迁移 1 条 |
| 接口 | 5 | 正常 1 + 参数非法 1 + 权限 1 + 重复提交（幂等）1 + 异常/超时 1 |
| 权限 / 数据可见性 | 角色数 ×关键操作（≥3） | 有权 1 + 越权 1 + 匿名/未登录 1 |
| 性能 / 容量 | 2 | 达标基线 1 + 超阈值降级 1 |
| 纯展示 / 文案 | 2 | 常规数据 1 + 极端数据（空 / 超长 / 多语言）1 |
| 需求描述本身不清 | 1 + notes | 只出 1 条锚定「当前理解」，其余等确认，别自创规则 |

**上限约束**（防用例爆炸，列表要能看得完）：单条需求默认不超过 **12** 条；
超出必须在 notes 说明为什么需要这么多（通常是判定表列数或状态迁移数天然就大）。

---

## 三、正向 / 负向配比

- 默认（「包含负向用例 = 是」）：**负向用例 ≥ 全集的 1/3**，且每条需求至少 1 条负向。
- 「包含负向用例 = 否」时仍然要保留**失败分支**与**空数据**两类——那是功能正确性的一部分，不是「负向」。
- 负向用例的价值全在预期结果的写法上：**必须写清「系统如何拒绝」**（提示文案 / 状态不变 / 不落库 / 返回码），
  只写「报错」「失败」等于没写（见 `case-style-rules.md`）。
- 不要生成「测试错误输入会报错」这种万能负向用例来充数——它验不出任何具体缺陷。

---

## 四、优先级分配（风险驱动，默认策略）

用例优先级取值固定为 `P0` / `P1` / `P2` / `P3`（服务端 `CASE_PRIORITY`，默认 `P1`；标签 `P0 关键 / P1 高 / P2 中 / P3 低`）。
**这是用例优先级，与需求的 `low/normal/high/urgent` 是两套值，不要混用、不要互相映射成同名字符串。**

### 判据：风险 = 出事概率 × 出事后果

| 用例优先级 | 判定条件（满足任一） | 典型用例 |
|---|---|---|
| `P0` 关键 | 主业务流必经路径；资金/账务/凭证正确性；权限绕过与数据越权；数据不可逆损坏（删除/覆盖/重复记账）；安全与合规强制项 | 「实盘金额与扣减金额一致」「越权访问他人单据被拒」 |
| `P1` 高 | 核心功能的分支与异常处理；接口契约（错误码、幂等、超时重试）；状态流转合法性与并发迁移；关键校验规则边界 | 「连续 5 次失败锁定账号」「重复提交只生成一张单据」 |
| `P2` 中 | 辅助功能、非关键边界、展示细节、提示文案、排序筛选、空态 | 「列表按创建时间倒序」「超长标题省略号」 |
| `P3` 低 | 极端罕见组合、锦上添花、多语言/无障碍、极端数据形态 | 「1000 条数据时的分页末页」 |

### 分配纪律

1. **`P0` 必须是少数**：一组用例里 `P0` 占比超过 1/3，说明没在做取舍，是在把风险推给「全是最高优先级」。
2. 负向用例、资金一致性、权限类**不得**被排到 `P2` 以下。
3. 优先级由**风险**决定，不由「这条好不好写」决定；也不要按需求 `priority` 机械平移（`high` 需求下也有 `P2` 的展示用例）。
4. 若生成偏好指定「优先级策略 = 均匀 / 仅关键」，按偏好执行并在 notes 记一句「优先级策略由偏好覆盖」。

---

## 五、需求拆分与 `reqNo` 规则

- 已有需求非空 → **复用优先**。判定「同一条需求」看语义不看字面：同一能力同一验收对象就是同一条，必须复用原 `reqNo`。
- 新需求 → 从已有最大编号顺延（`REQ-007` 之后是 `REQ-008`），**三位补零、连续、不跳号、不重号、不加子级**（`REQ-008-1` 这类写法禁止）。
- 一条需求只承载一个可判定能力。原文一段话讲了三件事 → 拆三条，各自给 `sourceRef`。
- 非功能需求（性能、安全、兼容、可用性）**也要单列成需求条目**，否则它们永远不会出现在覆盖统计的分母里，等于宣布「100% 覆盖」。
- 粒度下限：能写出一条用例的才算需求条目；写不出用例的（纯背景、目标口号）不要拆进来。

---

## 六、重复生成与幂等（对应验收「同一份 PRD 二次生成不产生重复用例」）

系统靠 `source_key` 去重（服务端按 PRD 内容与用例标识计算），但 AI 的输出稳定性直接决定去重能不能命中：

1. **同一需求的同一测试意图，标题措辞要稳定**——不要一次写「密码错误时提示」一次写「使用错误密码登录失败」，
   那会被判成两条用例，用户看到的是重复用例。
2. 不要在任何字段里掺入随机内容（时间戳、序号、"v2"、"补充"、"最终版"）。
3. 不要为了显得多而把已有用例换个说法再写一遍。
4. 二次生成时若已有用例清单被一并给你，**逐条比对**，已存在的测试意图不再重复输出，需要补的是缺口分支（并在 notes 说明补了哪几条、为什么）。

---

## 七、缺口与补生成

- 输出结束前自检：把「本次分块范围的需求」与 `cases` 里的 `reqNo` 集合做差集，**非空就必须处理**——要么补用例，要么在 notes 逐条写明为什么补不了（PRD 无该需求细节 / 依赖外部系统 / 需人工确认）。
- 补生成轮（系统提示「以下需求未覆盖」）：**只输出这些需求的用例**，`requirements` 输出 `[]`，不要顺手重写别的需求。
- 确实测不了的需求（如纯第三方行为）也要给 1 条「可观测点 + 判定方式」的用例或明确记入 notes，由人工在草稿视图勾掉，而不是留空。
