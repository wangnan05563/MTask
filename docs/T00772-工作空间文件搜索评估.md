# 评估：AI 控制台工作空间是否需增加文件搜索以支撑代码分析

> T00772 · 2026-09-18 · 评估对象：MTask AI 控制台（AI 工作台）与「工作空间」功能模块
> 参照标杆：Trae（官方文档 docs.trae.cn / trae.ai 博客）、WorkBuddy（官方 docs workbuddy.cn）
> 现状依据：MTask 源码一手调研（本文所有「现状」描述均对应具体实现文件，见附录）

---

## 一、结论

**需要，但不需要一步到位照搬 Trae/WorkBuddy 的全套索引体系。**

- MTask 的定位是「任务开发管理工具」，工作空间上下文的目标是**让 AI 卡片与任务处理具备基于真实代码的分析能力**，而不是做成 AI IDE。
- 现状的工作空间能力只到「路径注入 + 目录树采样」两级，Agent 无法回答任何**跨文件的具体代码问题**（如"哪个模块实现了扣费逻辑"），这是明确的硬缺口。
- 建议**分三级补齐**：P0 做关键词文件搜索 + 按需读文件 + 忽略配置（1~2 天量级，解决"找得到"）；P1 做轻量符号索引（解决"读得懂"）；P2 视需求再做向量语义检索（解决"搜得准"）。**P0/P1 即可支撑当前 AI 控制台卡片的代码分析场景，P2 在项目规模超过千文件前不必要。**

## 二、竞品能力拆解（基于官方文档，可验证）

### 2.1 Trae（AI IDE，字节）

| 能力 | 实现方式 | 触发方式 |
|---|---|---|
| 四级上下文引用 | #Code（符号级，LSP）/ #File / #Folder / #Workspace（项目级） | 聊天框 `#` 显式引用 |
| 工作区代码索引 | 对工作区文件做结构化扫描、分词、向量化，构建全局索引库；≤5000 文件打开项目时自动构建，>5000 需手动 Build | #Folder / #Workspace 依赖完整索引，AI 自动筛选最相关代码片段 |
| 忽略文件 | Ignore Files 列表（glob 模式），被忽略文件完全排除出索引——安全（防止索引密钥）+ 性能（排除 node_modules/编译产物） | 设置中心配置 |
| 文档集（#Doc） | RAG 典型应用：URL 自动爬取同路径三级内页面 / 本地 .md/.txt（单文件≤10MB、共≤50MB、≤1000 文件），向量化存储，文档内容作为最高优先级约束 | #Doc 引用，可绑定给 Agent |
| 联网搜索（#Web） | 实时 web 检索或指定 URL 抓取 | #Web + 问题 |
| Rules 规则系统 | 永久生效的 System Prompt 约束 | 全局/项目规则 |

**设计要点提炼**：Trae 的上下文体系 = *显式引用（#）+ 被动索引（#Workspace 自动召回）+ 排除机制（Ignore）+ 外挂知识（#Doc）* 四层；索引是"找文件"的底座，文件搜索发生在**语义层**（向量相似度），而非关键词层。

### 2.2 WorkBuddy（AI 编程助手）

| 能力 | 实现方式 |
|---|---|
| @ 引用体系 | @Files & Folders（文件/文件夹，含内容概览与目录导航）/ @Code（函数/类级代码块）/ @Docs（技术文档） |
| 工作空间索引 | 选择本地文件夹建立工作空间 → 索引文件结构与内容；用户提问时 AI **按需挑选相关文件读取**，不做全量灌入 |
| 知识库检索双通道 | 默认关键词匹配（grep 类字符串扫描）；向量化索引为**手动开关**（知识空间高级选项，本地 bge-m3 模型，≥128 字符文档才参与） |
| 边界约束 | AI 只访问工作空间内文件，不主动翻整个硬盘 |

**设计要点提炼**：WorkBuddy 与 MTask 形态更接近（工作空间 + 任务式交互），其"**关键词检索默认可用、向量索引按需开启**"的分级策略，以及"AI 按需读文件而非全量灌入"的原则，对 MTask 最有参考价值。

### 2.3 共同模式总结

1. **检索是 Agent 的前置基础设施**：两家都把"按问题定位相关文件"作为代码分析的第一步，而非把整个项目塞进 prompt。
2. **分级引用粒度**：符号 → 文件 → 目录 → 工作区，粒度越细 token 成本越低、答案越准。
3. **排除机制与索引同等重要**：忽略配置直接决定信噪比与安全。
4. **向量索引不是第一步**：WorkBuddy 默认关闭向量索引；关键词/结构检索已覆盖大多数"定位"需求，向量解决的是"自然语言↔代码语义"的模糊匹配。

## 三、MTask 现状与能力缺口

### 3.1 现状盘点（对应实现）

| 环节 | 现状 | 实现 |
|---|---|---|
| 工作空间绑定 | 项目可绑定 workspace_path（「选择工作空间」按钮） | projects.workspace_path |
| 任务 AI 处理 | prompt 仅注入 workspacePath **路径字符串**，AI 看不到任何文件内容 | adapters（T00771） |
| PRD 生成（T00769） | 目录树采样（深度 3 / 150 项，忽略 node_modules 等）+ README 片段，注入 prompt | services/PrdGenService.loadWorkspaceContext |
| PRD 上下文反查 | 需求 → PRD 原文注入（保头保尾截断 6000 字符） | util/prdContext（T00763） |
| AI 控制台 | 5 张卡片（计划导入 / 离线周报 / AI 周报 / 原始需求生成 PRD / PRD 导入），均无代码检索能力 | ReportPage + 各 Panel |
| 文件搜索 / 符号索引 / 忽略配置 / 向量检索 | **均无** | — |

### 3.2 缺口识别（按"上下文利用效率"与"代码分析能力"两维度）

| # | 缺口 | 影响 |
|---|---|---|
| G1 | **无文件搜索**：Agent 无法按关键词/文件名定位文件，只能靠目录树"盲选" | 代码分析类问题（排查、溯源、评审准备）无法开展——这是硬缺口 |
| G2 | **无按需读文件能力**：即便"找到"文件，也没有安全的读取通道（大小限制/类型过滤/行号定位） | 找到了也塞不进 prompt，或一次灌爆上下文 |
| G3 | **无忽略配置**：目录树采样已有硬编码忽略列表（node_modules 等），但用户不可配置，敏感文件（.env、密钥）无保护 | 信噪比低 + 安全风险 |
| G4 | **无符号级理解**：无函数/类结构提取（AST/LSP），AI 对代码的理解只能靠全文 | 粒度粗、token 浪费、大文件无法分析 |
| G5 | **无语义检索**：自然语言问题 ↔ 代码语义匹配缺失 | "找实现"类模糊问题命中率低（关键词搜索可部分弥补） |
| G6 | 上下文**无预算管理**：目录树/文件片段的截断是硬编码常量，无统一的 token 预算分配策略 | 多上下文源叠加时（PRD + 源码 + 需求）容易互相挤占 |

### 3.3 必要性判断

- **文件搜索 + 按需读取（G1/G2）+ 忽略配置（G3）：必须新增。** 没有它们，"基于上下文的代码分析"在架构上不成立——现状只能做"感知项目形状"，不能做"理解项目内容"。且实现成本低（Node 原生 fs + 正则/grep 级检索即可），是 ROI 最高的一层。
- **符号索引（G4）：建议新增（轻量版）。** 不必上完整 LSP——用语言无关的启发式提取（函数/类/导出声明正则扫描，建 `路径→符号` 清单）即可让 AI 先看"项目有什么符号"再点名读文件，token 效率提升一个量级。
- **向量语义检索（G5）：暂缓。** 引入嵌入模型 + 向量库（本地 LanceDB/chromadb 或外部 embedding API）成本高、运维重；WorkBuddy 也默认关闭。触发条件：单项目源文件 > 2000 或关键词搜索召回率明显不足时再立项。
- **上下文预算管理（G6）：随 P0 顺带做**（统一 ContextBudget 常量与分配顺序），避免后续每个卡片各自硬编码。

## 四、建议方案（优先级排序）

### P0（建议本次立项）——「找得到、读得准」

1. **工作空间文件搜索 API**：`GET /api/workspace/search?projectId=&q=&glob=`——文件名匹配 + 全文正则/关键词检索（复用 PrdGenService 的忽略列表），返回 `{path, line, snippet}`（限 50 条）。*
2. **按需读文件 API**：`GET /api/workspace/file?projectId=&path=&offset=&limit=`——行号范围读取，单次上限（如 400 行 / 64KB），路径必须落在 workspace_path 内（防目录穿越），遵守忽略配置。
3. **忽略配置**：项目级 `.mtaskignore`（glob 语法，默认模板同 Trae：node_modules/dist/build/.env 等），存储在项目设置，搜索/采样/未来索引共用。
4. **上下文预算管理**：抽取统一 `ContextBudget` 工具（目录树 / 文件片段 / PRD 原文各占多少字符的分配与截断策略），替换 T00769 中的硬编码常量。

### P1（下一迭代）——「读得懂」

5. **轻量符号索引**：增量扫描源码文件（js/ts/py/java 等），正则提取函数/类/导出声明，落库 `workspace_symbols` 表（path/symbol/line/kind），文件 mtime 变化时增量刷新；为 AI 提供"项目符号清单"作为检索中间层。
6. **Agent 工具化**：把搜索/读文件/符号查询包装为 AI 卡片的可用工具（模型 function-calling 循环），让「AI 周报生成」「任务 AI 处理」等卡片能自主多轮检索代码，而非一次性注入。

### P2（按需再立项）——「搜得准」

7. **向量语义检索**：文件分块 + embedding API（或本地 bge-m3）+ 向量库（sqlite-vec/LanceDB），#Workspace 式自然语言召回；触发条件见 3.3。
8. **文档集（#Doc 对标）**：项目文档/外部 URL 的 RAG 外挂（可先复用 PRD 文档库 prd_docs 的既有机制扩展）。

### 明确不建议做

- 完整 LSP 集成（维护成本远超 MTask 场景收益）；
- 云端全量代码上传索引（与 Trae 不同，MTask 用户项目含敏感业务代码，保持本地检索边界，同 WorkBuddy 的"只访问工作空间内文件"原则）。

---

## 五、一句话给决策

**P0 三件事（搜索 API、读文件 API、忽略配置）建议立即做——它们是 AI 控制台从"文档处理工具"升级为"代码分析 Agent"的前提，成本约 1~2 天；符号索引随后；向量索引等规模到了再做。**
