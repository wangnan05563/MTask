## 2. 阻塞级缺陷（B）

### B1｜模板结构复刻清单不完整，按现文本实施必然与客户模板不一致

二次解析（`阜新银行-票据系统优化-工作量评估V2.0.xlsx`，openpyxl 只读）实测：

- 合并区实为 **28 个**，PRD 附录 A 记「20 个」——计数错。
- PRD §6.1/附录 A **漏记 4 处关键结构**：
  1. `I4:I5` —— 表头「估算比例」纵向合并两行；
  2. `I8:I31` —— **开发段的估算比例只有一格，纵向合并覆盖整个开发段**（明细区不是每行都有 I 值）；
  3. `C16:C18`、`C27:C28` —— 另两组中模块合并（PRD 只列了 C8:C11/C12:C15/C22:C23/C25:C26）；
  4. **R31「小计：」行** —— `E31..H31 = SUBTOTAL(9,X8:X30)`，开发段内小计；明细区末行不是数据行而是公式行。
- PRD §6.1 只写 R35 的 E 列实例，实测 **R35 在 E/F/G/H 四列各有一条** `=SUBTOTAL(9,X6:X34)/每人月工天标准`，**I35=`SUBTOTAL(9,I6:I34)`**；R40 同理 `E40..H40 = X35*(1+SUM(X36:X39))`，**I40=`SUBTOTAL(9,I35:I39)`**。
- PRD 说系数行「值来自配置」，实测 **R36~R39 本身是三点结构**：E/F/G 三列同值（0.06/0.06/0.05/0.06）+ H 列同样式 PERT 公式 + I 列 `=IFERROR($H$35*H{r}/$H$40,"")`。
- 附录 A 表述「`B6:D6`…`B37:D37` 各阶段行」不准确：阶段行合并为 B6/B7/B32/B33/B34，B35~B40 的合并属于**汇总与系数行**。
- 另发现模板自身一处可疑写法（非本 PRD 缺陷，但导出须决定保真还是纠正）：`I8 = IFERROR(H31/每人月工天标准/$H$40,"")` 引用的是 **H31 小计**而非 H8；配合 `I8:I31` 合并看，语义是「开发段整体比例」，**不是笔误**——PRD v1.0 未识别出这层语义。

**影响**：G2「逐格一致」与验收 7 不可达；客户在 Excel 里改一个值重算，结果会与 MTask 面板不一致。
**处置**：本报告的 §7 修订清单 C1~C5 已把上述结构补进 PRD §6.1 与附录 A。

### B2｜「小计行被双重计入」的实现陷阱未定义（数值正确性风险，最高）

模板 `SUBTOTAL(9,E6:E34)` 的范围**包含 R31 的 `SUBTOTAL(9,E8:E30)`**。Excel 的 SUBTOTAL 语义是**忽略范围内其他 SUBTOTAL 结果**，因此模板不重复计。PRD §4.4 只写「前端计算则用当前可见行求和以保持一致」——若实现者对同一区间朴素求和，**开发段工作量与报价人月直接翻倍**。

**处置**：PRD §4.4 已补硬性口径：前端汇总必须按「阶段行 + 开发明细行」累加并**排除小计行**，等价于 SUBTOTAL 嵌套忽略语义；新增单测断言「前端 Σ ≈ 模板 H35」；自检比例明确指向 **I40**（Σ阶段比例 I35 + Σ系数比例）应≈1，而非泛指「Σ估算比例」。

### B3｜「零新依赖」被误读为「能力已具备」：写活公式 / 中文命名区域在本仓零先例

- 全仓 `server/ web/ scripts/` grep：**0 处** cell `.formula` 用法。既有 exceljs 能力是「样式填充 + 加载用户模板」（`exportStyle.ts` 的 `solidFill/paintHeaderRow/…`、`report-builder.ts:19` 的 `wb.xlsx.load`），**从未生成过公式**。
- exceljs 写入公式**不带缓存值**：openpyxl `data_only=True` 回读必为 `None`。PRD §9「导出后回读解析断言」若按数值断言 → 假阴性；按 `data_only=False` 断言公式串 → 只能证明写了公式，不能证明算得对。
- `每人月工天标准` 这类**非 ASCII 命名区域**经 exceljs `definedNames.addEx` 写入并让公式解析成功，未经本仓验证。

**处置**：§11 前置 **E0 技术验证（Spike，P0）**，通过标准四条（最小产物：H 列公式 + 命名区域 + 28 处合并区）；§9 断言方式改写为「公式串断言 + 用 Excel/LibreOffice 打开取重算值」双轨。这也把原 R7 从「依赖能力边界」升级为「已识别的已知边界」。

### B4｜R3 的处置指向错误通道（作者对现系统的结论性误判）

实测：计划复杂度的批量补算**早已实现且可用**——
- 服务：`server/src/services/PlanComplexity.ts`（值域 1~5，代码 clamp，见 `PlanService.ts:731`）；
- 端点：`GET /api/plans/complexity/missing`、`POST /api/plans/complexity/backfill`（`routes/plans.ts:768/773`）；
- UI：`PlanPage.tsx:1549-1562`「复杂度补算」按钮；
- 且 `routes/plans.ts:766` 的注释正是 R3 的根因原文：「complexity 只在 PRD 导入时由 AI 给出，手工/Excel 导入与存量行恒为 NULL」。

PRD R3 与派生单 T01843 写成「复用 T01620 批量 AI 评估通道」——T01620 是**待办**批量 AI 评估卡的僵尸态修复，与计划复杂度无关。
**影响**：R3 的真实成本被高估（从「建通道」降为「跑一次 + 人工抽查」）。
**处置**：PRD R3 文本已改；T01843 描述已同步更正（改指 `/api/plans/complexity/backfill`）。

### B5｜估算数据归属与级联口径自相矛盾

§3.1 写「`project_id` FK 级联删除（与 `plan_tasks` 同口径）」，§7 写「计划删除/归档 → `estimate_items` 级联保留但视图过滤」。二者不可能同时成立；且 `plan_tasks` 实为**软归档**（`archived`/`archived_at`，`schema.ts:517-518`），并非物理删除。
**处置**：统一为「`estimate_items` 不设 `plan_id` 物理级联；计划行 `archived=1` 时随视图过滤并计入『脱离计划的估算 N 条』提示」。

### B6｜调研样本违反 PRD 自列的入选标准（削弱「不可虚构」这一硬约束）

§2.1 入选标准②=「近 12 个月有推送」，实测（GitHub REST，2026-10-11）：
- `taskjuggler/TaskJuggler` pushed_at = **2025-07-28**（14.5 个月）→ 不符；
- `dlmueller/PERT-Beta-Python` 停更于 2015 → 不符；
- `opf/openproject` PRD 记「活跃」未给日期 → 实为 **2026-10-10**。

**处置**：标准②改为仅约束「功能/UX 借鉴类」样本，算法对照类（⑤⑥）显式豁免；样本表补齐 OpenProject / TaskJuggler 实测推送日期。

### 8.2 E0 Spike 实测（PRD 升 v1.3，判据④「双轨断言」改「三轨」）

结论：**四条判据全过，E6 放行**；但过程中本报告 B3 的一条判断被实测推翻，据实更正：

- **推翻项**：v1.1 写「exceljs 写公式不带缓存值，openpyxl `data_only=True` 回读必为 `None`」——实测 exceljs `cell.value={formula,result}` 会同时写出 `<f>` 与 `<v>`，`data_only=True` 可直接读到数字。→ R8（预览显示空白）的缓解方案由「LibreOffice 重算」简化为「导出时落缓存值」；§9 断言口径由两轨改三轨（公式轨 / 缓存轨 / 重算轨）。
- **新增硬约束 1**：公式串**必须去前导 `=`**（exceljs 原样落进 `<f>`，`=SUM()` 会变成 `<f>=SUM()</f>`，openpyxl 回读成 `==SUM()`；本机 Excel 仍算对但属非规范形态）。
- **新增硬约束 2（最重要）**：**exceljs 读客户模板再写出，会丢弃常量命名区域** `每人月工天标准`（往返件 `defined_names=0`，Excel 打开后 `E35=#NAME?`；对照组模板副本 `E35=11.5`）。→ 原 R8 兜底里「附模板文件填充」的方案在 Node/exceljs 通道下不安全，E6 走从零构建 + 写侧注入命名区域。
- **新增硬约束 3**：openpyxl `load→save` 会把公式格缓存值清空（`E35 cached=None`），**严禁把 openpyxl 另存件当断言样本**。
- **通道分歧已澄清**：另有并行取证报「模板往返不丢常量命名区域」，那是 **openpyxl** 通道的结果；本 PRD 实现通道是 exceljs，以 §11.1 实测表为准。两条结论同时为真、不可互换。
- 数值轨依赖本机 GUI Excel 的 COM 自动化（机器无 LibreOffice），**不可进 CI**，列为发布前人工检查项。
