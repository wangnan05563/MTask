# T03280 2.2 迁移失败防护验证

> 验收项（原单）：幂等迁移、备份、重复执行测试和 API/落库断言；技术方案先评审。
> 取证时点：2026-10-28；取证方式：隔离数据目录起进程内真实 schema + 真实 express 路由。

## 1. 技术方案

| 环节 | 既有实现 | 结论 |
| --- | --- | --- |
| 建表/加列 | `initSchema()` 全量 `CREATE TABLE IF NOT EXISTS` + `ensureColumn()` 逐列探测 | 天然幂等，重复执行不产生差异 |
| 迁移前置快照 | `MigrationSnapshot.createMigrationSnapshot()` → `BackupService.runBackup('auto')` | 复用备份目录，落 `backups/mtask-backup-<YYYYMMDD-HHMMSS>.db` |
| 失败恢复路径 | 快照文件 + `BackupService.restoreBackup()` | 破坏性变更可通过快照整库回退 |
| 备份命名 | 时间戳到秒 | 同秒内重复调用不会互相覆盖（文件名相同即同一份快照） |

方案不新增代码路径：本单为「既有防护机制是否真的成立」的验证单，验证不通过才动实现。

## 2. 验证脚本

`D:/tmp/t03280-migrate-test.mts`（隔离目录 `D:/tmp/t03280-XXXXXX`，`MTask_DATA_DIR` 指向该目录，**不触碰生产库**）：

1. 连续执行 `initSchema()` 三次，比对 `sqlite_master` 全量指纹（表名+SQL 归一后排序拼接）与表数量。
2. 三次之间写入一条 project / task，校验重复执行后数据仍在。
3. 校验本期增量对象存在：`project_iterations`、`iteration_events`、`metric_day_snapshots`、`metric_day_cycle_samples`，以及 `ai_usage.card_key` 列。
4. `createMigrationSnapshot()` 后检查 `backups/` 下出现 `mtask-backup-*.db` 且 size > 0。
5. `runBackup('manual')` + `listBackups()` 可执行可列举。
6. 再次 `createMigrationSnapshot()`，确认可重复创建。
7. 进程内挂载真实 `server/src/routes/index.ts` 导出的 router，`POST /api/projects` 后**直接回读 sqlite** 校验落库内容与 API 返回的 id 一致，再 `GET /api/projects` 校验回读可见。

## 4. 结论

- 迁移路径在「重复执行 → 结构不变、数据不丢」这一维度成立（指纹逐字符一致，45 张表）。
- 迁移前置快照确实落在备份目录且非空，可与 `restoreBackup()` 组成回退闭环；同秒重复调用共享同一份快照，不会覆盖既有备份。
- API 层写入与 sqlite 落库内容一致，说明迁移后新库对上层契约无破坏。
- 未发现需要改实现的缺陷，本单无代码变更。

## 5. 已知边界

- 本次验证的是**当前 HEAD 的 schema 稳定态**；跨版本升级（旧库 → 新库）比对的等价保护由 2.2 的前置快照覆盖，不构造历史库样本。
- 快照粒度是整库，非按表；大库下快照耗时为秒级（708 KB 样本），生产库量级差异需在生产实例迁移窗口实测。
