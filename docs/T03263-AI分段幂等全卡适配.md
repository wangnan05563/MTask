> 单号：T03263（父需求 REQ-020「AI分段幂等全卡适配——补全 AI-103 分段幂等到所有支持长文生成的卡片」）

## 1. 全卡盘点：谁真的需要「分段幂等」

AI-103 的台账（`ai_gen_jobs` / `ai_gen_segments`）解决的是「一次生成被切成多段，某段失败/断流后重跑要能跳过已完成段」。所以盘点口径是**是否多段调用模型**，不是「是不是 AI 卡片」。

| 卡片 / 生成器 | 服务 | 调用模型次数 | 是否需要分段台账 |
| --- | --- | --- | --- |
| 代码审查讲稿 | `lectureStream.ts`（`LECTURE_CARD_KEY`） | 按模块切多段 | 已有（T03245/T03246） |
| 测试用例生成 | `TestCaseGenService.ts` | 拆分 1 次 + 每 5 条需求 1 块 | **本次补上** |
| PRD 生成 | `PrdGenService.ts` | 单次（长文靠输出预算，不切段） | 否：不存在「部分段已完成」的状态，重跑只能整体重调 |
| 阶段总结汇报 PPT | `summaryPptOutline.ts` / `summaryPptStream.ts` | 大纲 1 次 + 纯装配（不调模型） | 否：装配段无模型调用，失败重放成本为零 |
| 周报 / 报告导出 | `ReportService.ts` / `report-builder.ts` | 单次 | 否 |

结论：**当前真正「分段调模型」的只有讲稿与测试用例两张卡**，本次把测试用例补齐后，REQ-020 的「全卡」在现行代码结构下已无遗漏。单次调用的卡片若将来改成切段生成，应复用同一套 `declareSegments/beginSegment/finishSegment` 接口——台账是通用件，不需要为每张卡另立一套。

## 2. 测试用例卡接入方式

### 2.1 请求指纹决定 sectionKey

`TestCaseGenService.ts:178-185`：

```ts
const CARD_KEY = 'ai.testcase_gen';
const sectionKey = createHash('sha256')
  .update(JSON.stringify({ p: input.projectId, t: input.toolId, c: input.content, prefs: input.prefs ?? null, resplit: Boolean(input.resplitRequirements) }))
  .digest('hex').slice(0, 16);
const jobId = openJob({ cardKey: CARD_KEY, toolId: input.toolId, title: '测试用例生成', request: { projectId: input.projectId, sectionKey } });
const reused = doneSegmentsFor(CARD_KEY, sectionKey);
```

- 指纹含 PRD 原文、模型、偏好与「是否重新拆分」，任一项变化即视为**另一个请求**，缓存整轮 miss（负对照 D-01/D-03 验证此点）。
- `doneSegmentsFor`（`AiGenJournal.ts:202`）是本次新增的**跨任务**查询：按 `card_key + section_key` 取历史所有任务里 `status='done'` 的段，同一段键取最新一条。原来的 `reusableSegments(jobId)` 只在单任务内复用（讲稿「续作」用），不适合「上次跑完、这次重跑」。

### 2.2 需求拆分段

`TestCaseGenService.ts:222-232`：拆分段 `SPLIT_SEG='split'`，命中缓存时直接取回需求清单（并在面板提示），未命中才调模型；`resplitRequirements=true` 时强制跳过缓存。

### 2.3 用例块段

`TestCaseGenService.ts:307-311`：块键 = `cases:` + 该块需求的 `reqNo:title:content` 哈希——**按内容而非序号**，前置块失败导致分块边界漂移时仍能命中同一批需求的旧结果。

`TestCaseGenService.ts:369-390` 的重跑逻辑：

```ts
const cached = segOf(key);
if (cached) { …直接取回，不调模型… return; }
beginSegment(jobId, sectionKey, key);   // 失败才走到模型调用
```

失败只把那一段标 `failed` 并记错误，其余块继续；整轮结束按「失败块是否仍未被覆盖」定终态 `partial` / `done`（`:452`）。

### 2.4 复用也必须在新任务里落 done

一个易错点：从旧任务取回内容后若直接 `return`，**新任务**的该段会停在 `pending`，台账显示「未完成」，刷新恢复会误判进度并把用户拉回重跑。所以复用分支同样要 `beginSegment + finishSegment(ok:true, text)`（`:231-232`、`:376-377`）——内容来自旧任务，状态属于新任务。

## 4. 边界与未覆盖（据实登记）

1. **无 UI 恢复入口**：讲稿卡有 `GET /plans/code-review-lecture/jobs/latest`（`routes/plans.ts:217`）供刷新恢复；测试用例卡本次只落服务层台账，卡片页刷新后仍按原有方式重新发起，但重跑会自动跳过已完成块——功能收益在，恢复横幅不在。补恢复入口需要路由 + 面板改动，未纳入本单。
2. **指纹含 `toolId`**：换模型后缓存 miss，属有意行为（不同模型的拆分段/用例块质量不可互换）；代价是同 PRD 换模型重跑会全量重调。
3. **PRD 生成等单次调用卡片**：如实测已切成多段生成，需要另立单接入台账（见 §1 结论）。
4. **人工「停止」不走复用**：`signal.aborted` 时直接上抛，已落盘的 done 段保留在库里，下次重跑仍可复用。
