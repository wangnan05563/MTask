# PRD 导入流程优化方案（MTask 十期）

> 对象：`PRD-九期-B0主动派发入口与自动触发.md` v1.1，承接项目 **MTask十期**（projectId `586ae8c6-2e08-4180-86ba-732f1fab5006`）。  
> 结论：当前问题不是“AI 不会拆”，而是**导入链路没有全局 WBS 契约**——每片各造一套 WBS，合并只按标题去重，父子关系靠行序推断，占位行和需求类型混在一起，质量门只告警不阻断。  
> 本方案只做设计，不改库、不改代码。

## 1. 现状链路与问题

| 阶段 | 现有实现 | 当前行为 | 主要问题 |
|---|---|---|---|
| 1. 分片解析 | `PlanService.aiParsePrd` / `aiParsePrdChunked` | 长 PRD 切片后逐片调用 AI，每片输出“需求 + 里程碑 + 明细” | 提示词只“建议”分片不要另造 WBS，模型仍按片各产一套；没有代码级约束 |
| 2. 跨片合并 | `mergeChunkedPrdParts` / `mergePartDrafts` | 计划按**标题精确匹配**去重，保留首见，`reqNos` 取并集 | 不同片给同一功能起不同标题就合不掉；三套阶段原样拼接 |
| 3. WBS 归一 | `dedupeDraftsByNormalizedTitle` + `normalizeWbsGroups` | 归一化标题去重；按数字章号“回退”切套并顺延编号 | 只认 `1/2/3/M1` 数字章号；`P0-1/P1-2/EX/Q/F/R-*` 检测不到；顺延只是改编号，不是合并结构 |
| 4. 质量自检 | `analyzeImportQuality` / `normalizeWbs` | 统计并行 WBS、重复、占位、工期不符；用户可点“合并重复 WBS” | 指标只告警；一键归一化会“保留第一套、其余整段取消勾选”，丢独有节点 |
| 5. 落库 | `PlanService.importPrd` | 用 `milestoneDurations` + `intervalChildEdges` 按行区间算工期/父子；全量串行排期；全量建待办 | 父子按“里程碑之后、下一里程碑之前”推断，行序交错必错挂；里程碑也生成待办；174 行串行排到 2029 |
| 6. 前端导入 | `PrdImportPanel.doImport` | 只有版本冲突、覆盖缺口两个硬闸；WBS 套数/占位/描述不足只提示 | 质量不合格仍可一键落库；`normalizeWbs` 的“全取消”不可逆地丢覆盖 |

### 代码级证据

- `prdWbs.ts` 的 `isGapFillPlan` 用 `^REQ-\d{3}` 判占位，把所有 `REQ-` 标题都当成占位，误伤真实任务；`applySourceEntryGapFill` 把 `§x.y / Q / D / R / T / N / O / S` 都补成计划行。
- `milestoneChild.ts` 的 `intervalChildEdges` 明确按行位置区间挂父子；这是“4 测试与验收挂 22 条 3.x 任务”的直接原因。
- `PlanService.createPrdImportTodos` 对 `planTargets` 全量建待办，包括 20 个里程碑。
- `PlanService.importPrd` 的 `plans` 入参没有 `depsOn`，虽然 `createBatch` 已支持 `depsOn`（里程碑→child、普通→serial），PRD 导入通道没有把真实依赖接上。
- `PrdImportPanel` 的 `doImport` 只检查 `baselineRequired` 与 `coverageRequired`，`wbsGroups > 1`、`gapFillRows > 0`、`desc < 50` 都不阻断。
- `prdMerge.ts` 的多文件合并只重编号 + 拼接，没有 WBS 归一；服务端分片合并与前端多文件合并是两套口径。

## 2. 根因：缺的不是提示词，是“全局 WBS 契约”

1. **每片独立生成完整 WBS**：模型不知道全局阶段边界，只能各自造一套。
2. **合并按标题而不是按结构**：标题不同就合不掉；合掉也只是少一行，不会重建父子。
3. **父子靠行序而不是靠 WBS 编号**：`intervalChildEdges` 是“没有结构信息时的兜底”，现在却成了唯一口径。
4. **覆盖被误解为“每个编号一条任务”**：`§x.y`、`Q-xx`、`Dx`、`Rx` 是引用/决策/风险，不是工作项；补成计划行只会制造碎片。
5. **需求类型混装**：把风险、待确认问题、验收标准都塞进 `REQ-` 矩阵，制造 204 条“需求”，覆盖率虚高。
6. **质量门与落库脱节**：前端只告警，后端不校验；MCP 走 `importPrd` 也能绕过页面质量卡。

## 3. 目标流程：两段解析 + 结构归一 + 硬质量门

```
文档地图
  → 全局 WBS 骨架（1 次）
  → 分节填充（N 次，只填细节，不造阶段）
  → 结构归一（按 wbsCode/parentCode）
  → 质量门 + 树形预演
  → 用户确认
  → 落库（工期/父子/依赖/待办/排期）
```

### 3.1 文档地图（确定性 + 一次小模型调用）

在切片之前先产出一份 `DocumentMap`：

- 章节类型：`FR` / `NFR` / `AC` / `EX` / `RISK` / `OPEN` / `REF` / `CONTEXT`；
- 每类的编号与章节：`FR-1..6`、非功能表 11 条（性能/吞吐/可靠性/可观测/安全/兼容/可维护/可测试/可访问性/数据保留/端口）、`AC-1..30`、`EX-1..22`、`Q-xx`、`R-x`；
- 范围：P0/P1/P2/P3；
- 哪些章节只作上下文，不生成任务。

这份地图决定“哪些内容该变成任务、哪些只做验收/风险/引用”。当前 `applySourceEntryGapFill` 把所有编号都补成计划的逻辑应被移除。

### 3.2 全局 WBS 骨架（只调用一次）

用 `DocumentMap` + PRD §12 优先级规划，产出一个**唯一骨架**：

- 5~6 个里程碑；
- 30~40 个任务槽位；
- 每个槽位带：
  - `wbsCode`（如 `M2.3`）
  - `parentCode`（如 `M2`）
  - `phaseCode`（如 `M2`）
  - `priority`（P0/P1/P2/P3）
  - `sourceSection`（如 `6.2`）
  - `deliverable`（可独立验收的交付物）
  - `acceptanceRefs`（如 `AC-19`）
  - `dependsOn`（如 `M2.1`，`type: serial|parallel`）
  - `estimateDays`（0.5~5）
  - `taskType`（design/impl/test/ops/doc）

提示词只允许这一轮输出里程碑；后续分片**禁止新增里程碑**。

### 3.3 分节填充（按章节，不按“片”）

每一片只处理它包含的 `sourceSection`：

- 只允许填充已存在的 `wbsCode`；
- 允许在已有 `parentCode` 下新增任务，但必须带 `parentCode`，且要经过“新增任务”标记；
- 不允许产生新的 `phaseCode`；
- 若确实发现骨架缺失，输出 `proposedTasks` 而不是直接写入 `plans`，由质量门人工确认。

这样从机制上消灭“4 + 5 + 11 三套 WBS”，而不是靠提示词祈祷模型遵守。

### 3.4 结构归一（纯函数，服务端单源）

新增/改造纯函数：

- `deriveWbsTree(plans)`：按 `wbsCode`/`parentCode` 建树；无 code 的旧数据才回退到标题前缀。
- `structuralChildEdges(tree)`：父边来自 `parentCode`，不再来自行区间。
- `mergeWbsGroups(primary, secondaries)`：
  - 主 WBS 保留；
  - 第二套中与主套语义相同的任务合并（`reqNos` 并集）；
  - 主套没有的独有任务，按 `phaseCode`/`sourceSection` 映射到主套对应里程碑；
  - 映射不上的进入 `needsReview`，不静默丢弃。
- `detectWbsGroups` 扩展：
  - 数字章号回退；
  - `P0-*` / `P1-*` / `EX` / `Q` / `F` / `R-*` 等标签族切换；
  - 输出 `groupStartTitles` 与 `family`，不再只报“2 套”。

`intervalChildEdges` 保留，但降级为**legacy 兜底**：只有完全没有 `wbsCode/parentCode` 时才使用。

### 3.5 质量门：从“指标”改成“准入”

建议增加 `ImportReadiness = ready | needs_review | blocked`，至少以下硬闸：

| 闸门 | 阻断条件 | 处理 |
|---|---|---|
| WBS 套数 | `> 1` 且未选定主 WBS | 必须选主 WBS，并预览合并差异 |
| 里程碑数 | `> 8` | 阻断，要求收敛到 5~6 |
| 孤儿任务 | `parentCode` 不存在或无 child 边 | 阻断，要求修父子 |
| 占位/碎片 | 标题含 `§`、反引号、`|`、路径，或 `gapFill` 未处置 | 阻断，逐条改写成任务/验收/排除 |
| 描述不足 | P0/P1 任务 `< 50 字` 占比 > 10% | 阻断，要求补执行卡 |
| 验收映射 | AC 未映射到任何任务 | 阻断，要求补 `acceptanceRefs` |
| 范围 | P2/P3 任务进入当前计划 | 阻断，要求移到 backlog |
| 依赖 | 0 条 `serial/parallel` | 阻断，要求补真实前置 |
| 解析完整性 | 有缺失分片/截断 | 阻断，补解析或显式接受 |

对应 UI：

- 主按钮：`生成可执行计划`（仅在 `ready` 时可用）；
- 次按钮：`保存为草稿`（允许 `needs_review`，但不建待办、不排期）；
- 禁止用“接受缺口”一个 checkbox 绕过所有结构问题。

### 3.6 预演：从“计数”改成“树 + 差异”

`previewPrdImport` 增加结构结果：

- `tree`：里程碑 → 任务两级树；
- `issues`：每条阻断/告警的 code、对象、修复建议；
- `coverage`：FR/NFR/AC/EX 覆盖率，不是 `§/Q/D/R` 数量；
- `diff`：新增/合并/移动/归档的条数；
- `willCreateTasks`：只统计 `kind=normal` 且 `ready` 的任务。

### 3.7 落库：后端必须再校验一次

- `PlanService.importPrd` 入口调用 `validatePrdImportDraft(plans, requirements)`；不通过返回 422 + 结构化 `issues`，不能只靠前端。
- `milestoneDurations` 改为按 `parentCode`/树汇总；`interval` 只对旧数据。
- `createPrdImportTodos` 只给 `kind=normal` 建待办；里程碑不建普通待办，最多在阶段末尾建一条 `[里程碑验收]`。
- `planStarts` 从“全量按行串行”改为“按里程碑串行、里程碑内按依赖排”，P2/P3 不排期。
- `importPrd` 接上 `createBatch` 已有的 `depsOn`：`wbsCode → 实际落库标题/ID` 映射后写入，普通任务 `serial`、里程碑 `child`。
- 增加 `importBatchId`（计划/待办/批次表均可），支持“旧批次软归档 + 新批次导入”，不要靠标题手工清理。

## 4. 数据契约建议

`plans[]` 新增可选字段（不改变旧调用方）：

| 字段 | 用途 |
|---|---|
| `wbsCode` / `parentCode` / `phaseCode` | 结构归属，替代行区间 |
| `priority` | P0/P1/P2/P3，范围闸门 |
| `sourceSection` | 回溯 PRD 章节，生成任务卡 |
| `deliverable` | 一个可独立验收的交付物 |
| `acceptanceRefs` | AC-xx 映射 |
| `dependsOn` | 真实前置，`serial/parallel` |
| `estimateDays` / `taskType` | 粒度与工作类型 |

`requirements[]` 新增可选字段：

| 字段 | 用途 |
|---|---|
| `type` | `FR/NFR/CONSTRAINT`，不再把风险/问题/AC 混入 |
| `acceptanceRefs` | 需求与 AC 的关联 |

`coverage` 独立返回：

- `frCovered/frTotal`
- `nfrCovered/nfrTotal`
- `acCovered/acTotal`
- `exCovered/exTotal`
- `risks/openQuestions`（只做清单，不生成任务）
- `refs`（只做上下文，不阻断）

DB 可后置加列：`plan_tasks.source_ref`、`plan_tasks.wbs_code`、`plan_tasks.parent_code`、`plan_tasks.import_batch_id`、`prd_requirements.req_type`、`prd_requirements.acceptance_refs`。第一阶段可以先用 title/description 前缀承载，避免大迁移。

## 6. 对当前十期 174 条的处理建议

不建议在现有 174 条上继续“边裁边补”。推荐：

1. 先给当前 174 条打一个 `importBatchId`（或至少记录批次时间/PRD 文档 id）；
2. 按新流程生成 5~6 个里程碑、30~40 条任务的预览；
3. 预览通过质量门后导入新批次；
4. 旧批次 **软归档**（不物理删除），保留追溯；
5. 新批次导入时只建 normal 待办，不建 20 条里程碑待办。

目标指标：

- 里程碑 5~6；
- 执行任务 30~40；
- 孤儿任务 0；
- 占位/碎片 0；
- 里程碑待办 0；
- P0/P1 任务描述 ≥ 50 字或带执行卡；
- AC 覆盖率 100%；
- P2/P3 进入 backlog，0 条排期；
- 单任务 0.5~3 人日，上限 5 人日。

## 7. 分阶段落地

### 第一步：低成本高收益（1~2 天）

- 收窄 `isGapFillPlan`，停止误伤 `REQ-` 标题；
- `createPrdImportTodos` 跳过里程碑；
- 前端 `doImport` 增加 `wbsGroups>1`、`gapFillRows>0`、`description<50` 硬闸；
- `detectWbsGroups` 增加标签族检测，至少让质量卡不再把三套报成两套。

### 第二步：结构归一（3~5 天）

- 增加 `wbsCode/parentCode` 解析与 `deriveWbsTree`；
- `milestoneDurations` 与 `applyImportMilestoneChildEdges` 改用树；
- `normalizeWbs` 改为“选主 + 合并独有任务”，不再整段取消；
- `preview` 返回树形结构与 issues。

### 第三步：两段式解析 + 执行卡（1~2 周）

- 文档地图 + 全局骨架 + 分节填充；
- 需求类型拆分：FR/NFR/AC/EX/RISK/OPEN；
- 任务卡生成（目标、现状、改动文件、验收、依赖、验证）；
- 导入批次与旧批次软归档；
- 按阶段排期 + `depsOn` 真实依赖。

## 8. 验收标准

用这份 PRD 重跑，导入结果应满足：

- 5~6 个里程碑，30~40 条执行任务；
- 0 条 `§/Q/D/R/T/N/O/S` 碎片任务；
- 0 条 `REQ-` 误判占位；
- 0 条里程碑普通待办；
- 30 条 AC 全部有 `acceptanceRefs`；
- 6 条 FR、11 条非功能要求全部有任务覆盖；
- 22 条 EX 至少映射到异常处理/测试任务；
- P2/P3 0 条进入当前甘特；
- 依赖中至少存在 P0→P1、迁移→API 的 `serial` 边；
- 计划跨度不超过 2 个迭代窗口（按 1 个执行 Agent 估算）；
- 预演结果与实落库条数一致，重复导入可幂等/可批次归档。
