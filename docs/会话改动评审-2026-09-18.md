## 一、逐项审查发现

### 【高】H-1 updateIssue 允许「空结论 + resolved」——数据完整性缺口

**位置**：`server/src/services/PlanService.ts` updateIssue

```ts
if (patch.status === 'resolved' && patch.answer === undefined) {
  const cur = ... .answer;
  if (!cur.trim()) throw new Error('标记为已确认前请先填写结论（answer）');
}
db.prepare('... answer = COALESCE(?, answer), status = COALESCE(?, status) ...')
  .run(patch.question?.trim() ?? null, patch.answer ?? null, patch.status ?? null, ...)
```

**问题**：校验只在 `answer === undefined` 时查旧值。传 `{ answer: '', status: 'resolved' }` 会跳过校验（answer 非 undefined），随后 COALESCE 把已确认问题的结论**清空**。
**影响**：结论被清空的问题仍保持 resolved，且回写判重依赖 answer 非空——后续 writeback 会因 answer 为空被拒，行为不一致。
**触发场景**：任何直接调 API 的客户端（前端 PrdPanel 当前不会传空串，但 API 是开放面）。
**修复**：校验改为「最终生效的 answer 为空则拒」：

```ts
const finalAnswer = patch.answer !== undefined ? patch.answer : row.answer;
if (patch.status === 'resolved' && !String(finalAnswer).trim()) {
  throw new Error('标记为已确认前请先填写结论（answer）');
}
```
（需把 row 查询改为 `SELECT *` 取出 answer——当前只取了 status。）

### 【高】H-2 globToRegex 接受外部输入且无复杂度防护——ReDoS 风险

**位置**：`server/src/services/WorkspaceService.ts` globToRegex；入口 `GET /api/workspace/search?glob=...`（登录用户可控）。

**问题**：用户传入的 glob 直接转 RegExp 执行于全目录所有文件路径。恶意 pattern（如 `**a**a**a**b` 类嵌套量词组合）可造成灾难性回溯，阻塞整个同步路由（better-sqlite3/Node 单线程），形成 DoS。
**影响**：已登录用户可使后端长时间 100% CPU。
**触发场景**：构造 `glob=(a+)+$&q=aaaa...` 类请求。
**修复**（三选一，推荐 a）：
a. 入口白名单化——只允许 `[\w\-.*?/]` 字符且长度 ≤128，拒绝 `*` 连续超过 2 个：

```ts
if (glob) {
  if (glob.length > 128 || /(\*{3,}|\([^)]*$)/.test(glob)) throw new Error('非法 glob 模式');
}
```
b. 给 `re.test` 包执行超时（worker 内执行，成本高）；
c. `search` 的 glob 匹配改为「前缀/后缀/包含」三种受限语义，不走自由 regex。

### 【高】H-3 search 文件名命中分支绕过 glob 过滤

**位置**：`WorkspaceService.search`（约 L127）

```ts
if (relChild.toLowerCase().includes(needle)) {
  hits.push({ path: relChild, line: 0, snippet: '(文件名命中)' });
  continue;   // ← globRe 校验在后面的全文分支，此处被绕过
}
```

**问题**：`glob=*.md` 时仍会命中 `src/auth/login.ts` 的文件名，与文档语义（glob 限定文件类型）不符。
**影响**：结果集不符合调用方过滤预期（低危但属功能正确性）。
**修复**：把 glob 校验提到文件名命中之前：

```ts
if (globRe && !globRe.test(relChild)) continue;
if (relChild.toLowerCase().includes(needle)) { hits.push(...); continue; }
```

### 【中】M-1 organize 批量处理时每任务全目录扫描——性能隐患

**位置**：`AIService.organize`（T00777 注入点）。

**问题**：`organize(taskIds)` 循环内逐任务调 `WorkspaceService.autoContext` → 每个关键词做一次**全目录同步 IO 扫描**。批量 AI 梳理 10 个任务 × 最多 11 个关键词 = 最多 110 次全树遍历，且全部是同步 fs——大项目下事件循环被长时间阻塞，SSE/其他请求卡顿。
**修复建议**：organize 循环外先做一次「批量预扫描」：合并所有任务的关键词一次收集命中（或对 `(projectId)` 级做 memo 缓存，首扫后 5 分钟内复用）。最小改法——organize 里对已用过的 `projectId` 缓存 autoContext 结果按关键词分组复用。

### 【中】M-2 refreshSymbols / loadWorkspaceContext 全同步 IO 阻塞事件循环

**位置**：`WorkspaceService.refreshSymbols`（readdirSync/readFileSync 递归）与 `PrdGenService.loadWorkspaceContext`。

**问题**：数千文件的工作区首次刷新会同步阻塞数百 ms~数秒；期间 SSE 流（prd-generate-stream 正是长连接）与其他请求全部停摆。
**修复建议**：短期可接受（上限 5000 符号/150 项树有防爆约束），中期把 `refreshSymbols` 挪到 worker_threads 或改 `fs/promises`；至少在 generatePrdStream 的 stage 日志前 `await new Promise(setImmediate)` 让出事件循环。

### 【中】M-3 saveToPrdView 固定文件名导致同日重名堆积

**位置**：`web/src/pages/PrdGenPanel.tsx saveToPrdView`

```ts
const docName = `PRD-${new Date().toISOString().slice(0, 10)}.md`;
```

**问题**：同日多次生成会创建多份同名 `PRD-2026-09-18.md`（prd_docs 无唯一约束，列表出现多个难以区分的条目，且 T00770 矩阵「查看 PRD」无法分辨版本）。
**修复建议**：同名时追加序号或时间戳：

```ts
const base = `PRD-${new Date().toISOString().slice(0, 10)}`;
const docs = await api.get<Array<{ filename: string }>>(`/plans/prd-docs?projectId=${projectId}`);
let docName = `${base}.md`;
for (let i = 2; docs.some((d) => d.filename === docName); i++) docName = `${base}(${i}).md`;
```

### 【中】M-4 忽略规则双轨不一致：loadWorkspaceContext 不读 .mtaskignore

**位置**：`PrdGenService.loadWorkspaceContext`（自带 IGNORED_DIRS 硬编码）vs `WorkspaceService.loadIgnoreRules`（默认 + .mtaskignore）。

**问题**：同一工作空间，目录树采样与文件搜索的可见范围不同——用户在 .mtaskignore 里屏蔽的目录仍会出现在 PRD 生成的上下文里；且 PRD 路径也可能泄露用户想屏蔽的敏感目录名。
**修复建议**：`loadWorkspaceContext` 改用 `WorkspaceService` 的规则加载（导出 `loadIgnoreRules`/`isIgnored` 或提供一个 `WorkspaceService.listTree(projectId, opts)` 统一入口），删掉 PrdGenService 的私有 IGNORED_DIRS。

### 【中】M-5 父任务 progress 只在「子任务状态变更」时重算——新增/删除子任务不同步

**位置**：`TaskService.syncPlanOnStatusChange`（T00776 补 progress 列后暴露的语义缺口）。

**问题**：父任务在部分子任务完成后已 done（progress=100）；此后**再新增一个子任务**，父任务仍显示 done/100%，新子任务完成也不影响——进度语义失真。
**修复建议**：`TaskService.create`（有 parentId 时）与删除子任务路径各追加一次与 syncPlanOnStatusChange 相同的汇总调用（抽成 `recalcParentProgress(parentId)` 复用）。

### 【低】L-1 .mtaskignore 自身可被全文搜索命中

`search('secret')` 会命中 `.mtaskignore` 的规则行文本（本次测试 I-2 就是被它干扰后改词才通过）。规则清单泄露风险极低，但建议把 `.mtaskignore` 加入 DEFAULT_IGNORE_FILES 使行为自洽（或文档注明）。

### 【低】L-2 writebackIssue「节在文档首行」边缘产生重复节

`indexOf('\n' + SECTION + '\n')` 要求节标题前有换行——若 PRD 第一行就是该节标题则判不到，else 分支会在文末追加第二个同名节。触发概率极低（生成模板不会这样），修复：用 `/^## 待确认问题结论\s*$/m` 匹配行首。

### 【低】L-3 PrdGenService 死代码与冗余

`generatePrdStream` 里 `startedAt` 计时后仅 `void startedAt`——建议真正记入日志（`耗时 ${Date.now()-startedAt}ms`），否则删掉。同类：`FILE_SNIPPET_LIMIT` 已删但 `SEARCH_FILE_MAX_BYTES` 等常量位置合理。

### 【低】L-4 PrdPanel 编辑态点击同文档行会静默丢弃未保存编辑

`openDoc` 在 `mode === 'edit'` 时仍重新拉详情覆盖——建议编辑中点击同文档行时直接 return（或 askConfirm）。

### 【低】L-5 App.tsx 动画 dasharray 固定 26

`stroke-dasharray: 26` 对不同长度 path 的 lucide 图标视觉不一（短线段出现流动空档）。纯视觉，可改用 `pathLength="1"` + dasharray 0.3~0.7 归一化技巧。

### 【低】L-6 ReportPage 五卡片互斥开关手写重复

五处 `setShowX(false)` 互斥重置——建议抽 `const toggleCard = (k) => setShow({aiImport: k==='ai', ...})` 或单一 state 字符串。可读性问题，无行为缺陷。
