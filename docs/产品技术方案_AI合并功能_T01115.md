## 1. 前后端接口契约

### 1.1 POST /api/merge/preview —— AI 合并预览
```
请求体 { module: 'task'|'req'|'prompt',   // 模块类型（跨模块 400 拦截）
         ids: string[],                    // 2~10 条记录 uuid，服务端二次校验同模块
         toolId?: string }                 // AI 工具 id，缺省用全局默认
请求头 X-Access-Token + Idempotency-Key    // 稳定键 = sha256(module + ids 排序拼接)，前端生成
响应 200 { mergeId, title, content,        // content 为 Markdown
           usage: { model, durationMs, tokens } }
错误  400 参数/数量不合法｜409 幂等命中（该批已生成，返回原 mergeId 供直接确认）
      413 单条正文 >5000 字或总量 >20000 字｜504 AI 超时（askJson 已内置重试）
```
幂等实现：`merge_logs.merge_key` 唯一索引；重复 preview 直接返回既有结果（不重复计费）。

### 1.2 POST /api/merge/confirm —— 确认落库（单事务）
```
请求体 { mergeId, module, ids, title, content, toolId }
  // title/content 为用户预览阶段可能编辑后的最终文本
服务端事务：① 重校验全部 ids 存在且 merged_into 为空（任一已合并→409 并发冲突）
           ② 按模块创建新记录（tasks: status=todo；req: sort 追加；prompts: 新 prompt）
           ③ 原记录 merged_into = 新记录编号（不物理删除）
           ④ merge_logs.status='applied'，写 new_task_no
响应 201 { newRecord: {...} }  → 前端刷新列表并跳转新记录详情
```

### 1.3 GET /api/merge/logs?limit=50 —— 审计（P2，可后置）
返回入参摘要/出参全文/耗时/Token，供成本核算；明细入 merge_logs 表。

### 1.4 存储变更（ensureColumn / CREATE TABLE，均向后兼容）
```sql
ALTER TABLE tasks        ADD COLUMN merged_into TEXT;  -- 非空=已被合并（指向产物 task_no）
ALTER TABLE req_entries  ADD COLUMN merged_into TEXT;
ALTER TABLE prompts      ADD COLUMN merged_into TEXT;
CREATE TABLE merge_logs (
  id TEXT PRIMARY KEY, merge_key TEXT UNIQUE, module TEXT, ids_json TEXT,
  tool_id TEXT, model TEXT, title TEXT, content TEXT,
  input_digest TEXT, duration_ms INTEGER, tokens INTEGER,
  status TEXT NOT NULL DEFAULT 'pending',   -- pending → applied
  new_task_no TEXT, created_at TEXT NOT NULL
);
```
列表过滤：三菜单主列表默认追加 `AND COALESCE(merged_into,'')=''`（已合并记录从活跃列表消失）；归档区/详情页保留可见，记录上显示「已合并 → {产物编号}」可点击跳转。

## 2. AI Prompt 模板（askJson，输出强制 JSON）

```
system:
你是 MTask 的记录合并助手。你的任务是把多条同类记录合并为一份逻辑清晰的新记录。
铁律：
1) 只使用原文明确提及的信息，严禁虚构任何业务内容、数字、日期或名称；
2) 冗余重复的信息只保留一份，冲突信息如实并列标注（〔记录2〕…）；
3) 保留原文的具体细节（编号、路径、参数），不抽象化；
4) 只输出 JSON，格式：{"title": "新标题（≤40字）", "content": "新正文（Markdown，含必要的分节）"}

user:
模块类型：{task|req|prompt}
以下 {n} 条记录需要合并：
--- [1] {标题}
{正文，超 5000 字截断}
--- [2] {标题}
{正文}
...
请输出去重、重组后的合并记录 JSON。

retrySystem（askJson 二次重试用，压缩输出规模）：
在上述基础上追加：正文压缩到 800 字以内，只保留结论性内容。
```
调用参数：max_tokens=8192（按 PRD 场景预算规则，防长正文合并截断）、temperature 默认（重试自动降 0）。

## 3. 数据状态机

```
记录（task/req/prompt）:
  active ──confirm──▶ merged(merged_into 非空) ──「还原」──▶ active
  ▲ 主列表仅显示 active；merged 记录详情页显示「已合并 → 编号」跳转

merge_log:
  pending ──confirm 成功──▶ applied（写 new_task_no）
     │                        └─ 重复 confirm 同 mergeId → 409
     └─ 24h 未 confirm → 过期作废（列表可见、confirm 时校验创建时间）
```

## 4. 异常处理策略

| 场景 | 策略 |
|---|---|
| AI 网络超时 | askJson 内置 1 次自动重试（降温）；前端 Loading 上限 60s，超时提示「重试」——幂等键保证重试不产生重复计费记录 |
| 输出质量不达标 | 预览强制可编辑；「重新生成」按钮以同 merge_key 发起新 mergeId（旧 preview 自动作废） |
| 并发冲突 | confirm 事务内重校验全部 ids 未合并；任一冲突整体 409 回滚，前端提示并刷新 |
| 内容超长 | 服务端硬校验 413（单条 5000 / 总量 20000 字）；前端勾选时实时提示 |
| 跨类型/跨模块 | preview 服务端校验 module 与 ids 归属一致性，401/400 拦截；前端按钮在跨 tab 勾选场景天然隔离 |
| 重复点击 | 按钮 busy 态 + mergeId 状态机 + merge_key 幂等三层防护 |

## 5. UI 交互关键节点

1. **勾选**：三页多选模式（任务页复用现有 selectedIds；需求/提示词页新增同款勾选列+全选）；「AI 合并」按钮置于批量工具栏，`n<2` 置灰 + title 提示「请至少选择 2 条」，`n>10` 点击时提示。
2. **生成中**：弹窗 + Loading（aispin + 「正在语义合并 N 条记录…」）；超时出「重试」按钮。
3. **预览**：新标题/新正文**可编辑**（Markdown 编辑器，与任务描述编辑器同款）；「原文对照」折叠标签（每条原记录一栏，展开对照）；「重新生成」。
4. **确认**：confirm → 刷新列表（新记录置顶 + flush 高亮动画——复用 refreshFlash）→ 跳转新记录详情；原记录从列表消失（归档区可查，带「已合并 →」链接）。
5. **审计**：设置 → 数据维护 tab 加「合并记录」只读列表（P2）。

## 7. 评审决策点

1. 「已合并」记录是否默认从活跃列表隐藏（本方案：隐藏、归档可查可还原）——或保留在列表加灰标？
2. 合并产物归属：新任务进原项目（本方案）；提示词进原分类。
3. Token 计费归属：计入 merge_logs 独立审计（本方案），不混入 ai_usage 业务统计口径（避免污染成功率指标）。
