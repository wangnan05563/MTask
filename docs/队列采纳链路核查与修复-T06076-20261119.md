# 队列「采纳」链路核查与修复（T06076）

- 核查时间：2026-11-19
- 范围：队列菜单 → job 回执 → 采纳 → 任务「处理结果 / AI 摘要」展示
- 结论：**采纳写错了字段**。旧实现把回执写进 `ai_summary`，从不写 `handle_result`，所以任务详情的「处理结果」页签必然为空；已修复并完成隔离库 + UI 实测。第二轮已补：回执质量门、默认「采纳才完成」、移动端采纳/撤回、采纳撤销。第三轮已补 P1（历史标记/旧入口/撤回边界/待采纳汇总/自动完成与检索开关/检索链路）并完成生产安装包 0.1.1119.273 部署与 T06076 重采纳。

## 一、现象与生产数据证据

| 字段 | 实测值 |

| `verified` | `0` |
| `ai_state` | `''` |

| `ai_summary` | 789 字（含「今日资讯阅读摘要」正文） |
| `ai_summary_at` | `2026-11-19T01:32:18.881Z` |
| `updated_at` | `2026-11-19T07:07:35.053Z` |

对应队列 job：

| 字段 | 实测值 |
| --- | --- |
| `status` | `success` |
| `response_payload` | 789 字 |
| `sent_at` / `finished_at` | `01:29:49.688Z` / `01:29:57.080Z` |

任务事件只有 `status: todo → done`（01:29:57 由队列成功自动回写），**没有 `result` 事件**——说明 01:32 那次「采纳」完全没走结果写入通道。

前端表现：刷新后「处理结果」页签仍是「（暂无处理结果，AI 分析结论将回写于此）」，而同样的 789 字出现在「AI 摘要」页签。

## 二、根因

### 2.1 主因：采纳落错字段

`server/src/services/TaskService.ts:1461` 旧实现：

```sql
UPDATE tasks SET ai_summary = ?, ai_summary_at = ?, status = 'done', updated_at = ? WHERE id = ?
```

- 只写 `ai_summary`，`handle_result` 从未被赋值；
- 任务详情两个页签的数据源本来就是分开的：`处理结果` 读 `handle_result`，`AI 摘要` 读 `ai_summary`（`TaskDetailDrawer.tsx:323–324、410–442、590`）；
- 产品文案也自相矛盾：`HelpTab.tsx:703` 写「把处理结论回传任务『处理结果』并显式回写 AI 状态」，`guides.tsx:258` 与采纳按钮 tooltip 却写「写入任务摘要」。

### 2.2 次生问题：采纳绕过 `TaskService.update()`

旧实现直接裸 SQL：

- 不写 `task_result_history`（旧结果无留档、无法回滚）；
- 不写 `task_events`（时间线看不到「处理结果回传/更新」）；
- 不触发计划↔待办联动（关联计划的 `plan_tasks` 不会同步 done/100%）；
- 不触发结果记忆抽取；
- 不回收 `ai_state`：任务可能停在 `done + AI 处理中` 的互斥态（实测 T06087 采纳后仍显示「AI 处理中」，直到本轮修复）。

### 2.3 体验缺口：队列行没有「已采纳」持久标记

`queue_jobs` 原表只有 `status/response_payload/...`，没有采纳态列。刷新后按钮重新出现，无法判断是否已采纳，重复点击会重复覆盖摘要。

## 五、其他质量检查结论

> 以下 5 项已在第六节完成修复与验证；本节保留第二轮修复前的原始发现与证据。

1. **队列成功会先把任务置 done（默认开启）**：`QueueService.autoCompleteQueueTask` 在 job 成功时即 `todo → done`，早于人工采纳。因此 T06076 在 01:29:57 就已完成，01:32 的采纳只是补文本。若产品口径是「采纳才算闭环」，应把 `queue.autoCompleteTask` 设为 `0`，否则会出现「done 但处理结果为空」的窗口期。
2. **回执内容质量不达标**：T06076 的 789 字回执开头自述「知识截止于 2026年7月，无法实时检索 2026年11月19日资讯」，正文为知识库背景整理，且 **0 个来源 URL**（任务明确要求「标注来源」）。当前队列工具（Agnes / DeepSeek / Groq 等）均为普通 LLM，无联网检索能力；此类「今日资讯」任务应改用具备检索能力的工具，或人工核对后再采纳。
3. **历史数据仍错位**：T06076 生产库 `handle_result` 仍为空、`ai_summary` 仍是回执正文。代码修复需重启 MTask 客户端/服务后生效；重启后在原队列对 T06076 再点一次「采纳」，即会把同一段回执写入处理结果（`adopted_at` 初始为空，按钮会重新出现）。旧 `ai_summary` 不会被自动清理，可在「AI 摘要」页签重新生成总结覆盖。
4. **移动端队列只读**：`MobileQueue.tsx` 明确不提供增删改排，也没有「采纳」入口；移动端无法闭环，需回桌面端操作。
5. **采纳不可撤销**：采纳后无「撤回」按钮；如需改回，只能在任务详情编辑处理结果，或从「结果历史」恢复上一版。

## 六、第二轮修复（其他质量发现闭环）

### 6.1 回执质量门（发现 2）

- 服务端新增 `QueueService.receiptWarnings(job)`，识别三类风险：
  - `stale`：回执自述「知识截止 / 无法实时检索 / 无法联网」等；
  - `no_source`：任务描述要求「来源/出处/引用/链接/标注」，但回执正文无 `http(s)` 链接；
  - `placeholder`：含 `TODO / 待补充 / 未生成` 等占位词。
- `GET /api/queues/:id` 为每个 job 附带 `quality_warnings`；桌面/移动队列显示「质量待核（n）」。
- 采纳前前端弹确认列出每条风险；服务端 `adoptJob(..., force)` 对 blocking 警告强制拦截：不带 `force` 返回 400，带 `force` 才写入。普通 LLM 无法“修复”实时性，质量门的作用是阻止不可核验内容被静默转成正式处理结果。
- 实测：T06076 命中 `stale + no_source` 两条；无 `force` 返回 400「回执质量待确认…」；`force=true` 采纳成功；干净回执（含来源 URL）无需 `force` 直接采纳。

### 6.2 完成时机（发现 1）

- `autoCompleteQueueTask` 默认改为：队列成功**只标记 `ai_state=unread`，任务保持 `todo`**；不再自动 `done`。
- 保留旧行为为显式开关：`app_settings.queue.autoCompleteTask=1` 时仍自动完成。
- 实测（隔离库 + `sendAll` stub）：
  - 默认：`status=todo, ai_state=unread, handle_result=''`；
  - `queue.autoCompleteTask=1`：`status=done, ai_state=unread`。
- 这样「回执已产出」和「任务已完成」分开，采纳才是闭环，消除「done 但处理结果为空」窗口。

### 6.3 移动端闭环（发现 4）

- `MobileQueue.tsx` 增加「采纳」「撤回」按钮、质量提示确认、`已采纳` 徽标与警告计数；监控区仍保持只读。
- 实测：移动端打开 `2026-11-18 开发队列` → T06076 可见「采纳」；点击后弹 2 条质量提示，确认后显示「已采纳」+「撤回」；撤回后按钮恢复、徽标消失。

### 6.4 采纳撤回（发现 5）

- `queue_jobs` 新增 `adopt_snapshot`（采纳前 `status / handle_result / ai_state` 的 JSON）。
- 新增 `unadoptJob(queueId, jobId)` 与 `POST /api/queues/:id/jobs/:jobId/unadopt`：恢复采纳前结果与状态，清空 `adopted_at / adopt_snapshot`。
- 安全阀：若采纳后处理结果被人工修改（与回执正文不一致），拒绝自动撤回，避免覆盖新内容。
- 实测：
  - 采纳后 `handle_result=787`、`ai_summary=789`、`adopted_at` 有值；
  - 撤回后 `handle_result=0`、`status=todo`（采纳前是「done + 空结果」的坏状态，按 P1 边界回退为待办）、`adopted_at=''`；
  - 人工改写结果后再撤回：400「处理结果在采纳后已被修改，无法自动撤回」。

## 八、第三轮：P1 收口 + 生产部署（2026-11-19）

### 8.1 历史采纳标记与旧入口兼容

- 启动期回填：`queue_jobs.status='success'`、`response_payload` 非空、且 `tasks.handle_result` 与回执逐字一致（忽略空格/CRLF）时，用 `finished_at` 回填 `adopted_at`；不会把「误写到 ai_summary」的旧记录误判为已采纳。
- 旧入口 `POST /api/tasks/:id/adopt` 改走 `QueueService.adoptTaskContent`：按任务最近成功回执逐条比对正文，命中则走 `adoptJob`（补 `adopted_at` + 撤回快照），匹配不到才回退旧逻辑。
- 历史回填的 `adopted_at` 没有快照，撤回时明确拒绝（「历史采纳记录，没有可恢复快照」），不伪造恢复。

### 8.2 撤回边界

- 采纳前为「done + 空处理结果」时，撤回后回落 `todo`，避免再次制造「已完成但处理结果为空」的矛盾态；有实际旧结果时仍恢复原状态。
- 人工改写结果后撤回仍返回 400，不覆盖新内容。

### 8.3 队列列表待采纳提示

- `QueueService.summary()` 新增 `job_unadopted`（成功 + 回执非空 + `adopted_at` 空）。

### 8.4 队列设置开关
