# Git 视图同一分支多仓库展示区分方案

> 任务：T04525  
> 范围：AI 工作台「Git 增量资产提取」与「Sonar 质量扫描」共用的 Git 视图  
> 约束：不修改 Git 数据模型与接口定义，不做大规模重构，仅落视图层方案

## 1. 现状与问题

当前两条卡片的范围层由 `web/src/ui/gitScopePicker.tsx` 维护，`projectIds` 对应 MTask 项目，`taskIds` 对应已回写提交的任务。服务端 `server/src/services/lectureGitLog.ts` 的 `/git/log` 只接收一个 `projectId`，再解析该项目的 `workspace_path` 并调用 Git 采集；`web/src/ui/GitTreePickerModal.tsx` 一次只展示一个项目仓库的提交图。

这个设计带来三个问题：

1. **仓库身份不可见**：提交行只显示短 SHA、标题、作者、时间和本地引用名。当 BEMP 类场景中多个仓库都存在同名分支时，用户只看到重复的分支 chip，无法判断某一条提交属于哪个仓库。
2. **分支不能天然聚合**：`GitRefName.name` 是分支名，缺少仓库维度。即使两个仓库都有 `release/2.3`，现有视图也无法把它们识别成一个同名分支的多个仓库实例。
3. **跨仓库执行语义不能由前端擅自合并**：`gitScopePicker.tsx` 明确要求多项目使用同一个 `workspace_path`，`server/src/services/gitExtract.ts` 也按单一工作空间解析提交。不同仓库的提交 SHA、父提交、文件路径和历史彼此独立，视觉层强行合并会让用户以为可以一次跨仓库采集，但现有执行链路做不到。

因此，本方案的目标不是把多仓库提交图伪合成一棵树，而是在不改变数据模型和接口的前提下，把“分支 -> 仓库 -> 提交”的隶属关系显式呈现出来；跨仓库执行保持逐仓库边界。

## 2. 设计原则

1. **分支名是视觉锚点，仓库是归属分组**：同名分支先聚合显示，仓库作为分支下的子分组，而不是让分支在多个仓库间反复重复。
2. **不制造不可执行的假合并**：同一分支可展开查看多个仓库；只有当前工作空间内的提交集能够参与当前提取/扫描任务。若用户选择跨仓库仓库组，界面必须明确提示“当前执行仍按仓库拆分”。
3. **兼容现有数据结构**：继续以 `Project.name`、`Project.workspace_path` 和 `/git/log` 返回的 `refs` 作为视图输入，不新增数据库字段，不改 API 请求/响应契约。
4. **适配卡片空间**：默认折叠仓库组，只暴露“分支 + 仓库数”；展开后才显示每个仓库的提交行，避免多仓库场景把弹窗横向撑爆。
5. **与 MTask 风格一致**：沿用现有 `PILL`、`FIELD_QUIET`、`var(--accent)`、`var(--surface)`、`var(--text-muted)` 和 lucide 图标，不引入新的视觉语言。

## 3. 仓库分组策略

### 3.1 视图层分组键

在组件内定义一个纯视图函数，不进入服务端：

```ts
interface RepoBranchGroup {
  branchKey: string;
  branchName: string;
  repos: Array<{
    projectId: string;
    projectName: string;
    repoLabel: string;
    workspacePath: string;
    commitCount: number;
    available: boolean;
    unavailableReason: string;
  }>;
}
```

- `branchKey = branchName`。本地分支优先，其次是 `origin/<branch>` 的 `<branch>`；tag 不参与同名分支聚合，单独走“标签”分组。
- `repoLabel` 默认取 `Project.name`；若同名项目或项目名不足以区分，取 `workspace_path` 的最后一段目录名作为补充。
- `commitCount` 表示当前仓库在当前页/筛选窗口内该分支可见的提交数量，只作引导，不承诺历史全量。
- `available = workspace_path` 非空且该仓库取数未失败；失败仓库仍保留分组行，显示具体原因，不静默隐藏。

### 3.2 分组数据来源

不新增接口，只并发复用现有 `GET /git/log?projectId=...&all=1`：

1. Git 树弹窗已持有 `projects` 列表。若选中分支属于跨仓库场景，前端按“当前可见仓库列表”逐项调用现有端点。
2. 每个响应都带 `projectId` 和 `workspacePath`，前端据此标记仓库归属。
3. 使用 `Promise.allSettled`，一个仓库失败不影响其他仓库的分组展示。
4. 并发上限建议 3。若仓库超过 3 个，分批取数，避免一次打开弹窗就触发大量 Git 子进程。

### 3.3 聚合展示层级

```
分支：release/2.3                       3 个仓库 · 24 个提交
├─ 仓库：BEMP-portal      · D:/code/bemp-portal      · 10 个提交
├─ 仓库：BEMP-service     · D:/code/bemp-service     · 9 个提交
└─ 仓库：BEMP-job         · D:/code/bemp-job         · 5 个提交
```

分支行是折叠组，仓库行是第二层，提交行是第三层。默认展开当前项目对应的仓库，其余仓库折叠；用户展开某个仓库时才懒加载其 `/git/log` 分页。

## 4. 视觉区分方案

### 4.1 层级与缩进

- 第一层：分支名 + 仓库数 + 提交总数。分支名使用 `var(--text)`，统计信息使用 `var(--text-muted)`。
- 第二层：仓库组行使用 12px 缩进，左侧保留一条 2px 的浅色竖线。仓库名使用 `var(--text-secondary)`，工作空间路径使用等宽字体和 `var(--text-muted)`。
- 第三层：提交行沿用现有车道图、短 SHA、标题、时间、作者。车道图只在同一仓库的提交集合内计算，不做跨仓库车道拼接，否则父提交不存在时会画出误导性的假连线。

### 4.2 颜色与图标

- 分支行左侧用 `GitBranch` 图标，颜色 `var(--accent)`。
- 仓库行左侧用 `FolderGit2` 图标，颜色 `var(--text-muted)`；当前项目对应的仓库使用 `var(--accent)`。
- 同名分支的多个仓库共享一个中性背景：`var(--surface)`。当前选中仓库行使用 `var(--surface-2)`。
- 不使用大色块区分仓库。多仓库颜色过多会破坏 MTask 卡片的一致性，且对色弱用户不友好；文本仓库名是主要标识，颜色只作辅助。

### 4.3 徽标与状态

| 状态 | 展示 | 说明 |
|---|---|---|
| 当前仓库 | `当前` | 优先默认展开，用于承接用户刚才在范围层选择的上下文 |
| 备用仓库 | 仓库名 | 折叠状态，不干扰当前选择 |
| 未绑定工作空间 | `未绑定` | 保留仓库行，禁用展开与选择 |
| 取数失败 | `不可用` | 展开/悬停显示 `/git/log` 返回的一句话原因 |
| 跨工作空间 | `跨仓库` | 允许查看，但禁用“合并执行”期望，提示逐仓库处理 |

## 5. 交互设计

### 5.1 进入视图

1. 用户从 Git/Sonar 卡片打开 Git 视图。
2. 弹窗先保留现有单仓库体验，避免无多仓库需求时增加认知成本。
3. 当同一分支名在多个 `Project.workspace_path` 中都能被识别时，分支 chip 变成 `release/2.3 · 3`。数字表示仓库数。
4. 用户点击 chip 后进入分支聚合视图。

### 5.2 展开/收起

- 分支行点击切换整个分支组。
- 仓库行点击只切换该仓库的提交列表。
- `Ctrl/Cmd + 点击` 仓库行不改变当前仓库，仅作为展开/收起；避免用户误把“查看”当成“切换执行上下文”。
- 展开、收起状态存入 `useSessionState('git.tree.repoGroups', ...)`，会话内刷新或重开弹窗后保持。

### 5.3 选择与确认

1. 单仓库选择：行为完全保持现状，确认后回传该 `projectId` 和 SHA 集合。
2. 跨仓库查看：用户可以浏览多个仓库，但当前一次确认只允许选择一个仓库的提交集合。
3. 若产品后续需要跨仓库合并执行，应另开后端任务；本方案不在前端把多个仓库的 SHA 伪装成同一条执行链路。

### 5.4 筛选与搜索

- 分支筛选作用于分支组。
- 仓库筛选提供下拉：`全部仓库 / 当前仓库 / 具体仓库`。
- 搜索提交标题、SHA 或作者时，命中结果按 `分支 -> 仓库 -> 提交` 归位；若命中发生在未展开仓库，仓库行显示“命中 N”徽标。

## 7. 关键伪代码

```ts
function branchNameOf(ref: GitRefName): string | null {
  if (ref.type === 'tag') return null;
  if (ref.type === 'remote') return ref.name.replace(/^origin\//, '');
  return ref.name;
}

function mergeRepoRefs(projectId: string, refs: GitRefName[]) {
  const byBranch = new Map<string, number>();
  for (const ref of refs) {
    const branch = branchNameOf(ref);
    if (!branch) continue;
    byBranch.set(branch, (byBranch.get(branch) ?? 0) + 1);
  }
  return [...byBranch.entries()].map(([branchName]) => ({
    projectId,
    branchName,
  }));
}

function groupBranchesByRepos(repoRefs: RepoRefs[]): RepoBranchGroup[] {
  const map = new Map<string, RepoBranchGroup>();
  for (const repo of repoRefs) {
    for (const item of repo.branches) {
      const group = map.get(item.branchName) ?? {
        branchKey: item.branchName,
        branchName: item.branchName,
        repos: [],
      };
      group.repos.push(toRepoRow(repo));
      map.set(item.branchName, group);
    }
  }
  return [...map.values()]
    .filter(group => group.repos.length > 0)
    .sort((a, b) => b.repos.length - a.repos.length || a.branchName.localeCompare(b.branchName));
}
```

建议实现顺序：

1. 先落纯函数 `branchNameOf`、`groupBranchesByRepos` 和并发取数工具，并补 Node 测试。
2. 再改 `GitTreePickerModal` 的分支 chip 与折叠分组 UI。
3. 最后接入 Git 增量资产提取和 Sonar 质量扫描两个卡片，因为它们已经共享 `gitScopePicker` 和 `useGitScope`。

## 9. 需要明确的风险

1. **同名不等于同源**：两个仓库的 `release/2.3` 可能语义相同，也可能只是命名巧合。视图只能按分支名聚合，不能暗示两个分支指向同一代码状态。
2. **SHA 跨仓库无意义**：相同短 SHA 在不同仓库中可能完全不同；所有提交详情都必须带仓库上下文。
3. **车道图不能跨仓库拼接**：`assignLanes` 只应作用于同一仓库的提交集合，否则会把不存在父子关系的提交画成一条线。
4. **执行边界必须显式**：当前提取和扫描引擎按单一工作空间运行。多仓库视图可以协助定位，但用户选择后仍需按仓库分别执行，UI 不应提供假的“一键跨仓库合并”。

## 10. 验收要点

1. 单仓库场景默认仍显示原有提交图，无新增折叠层级。
2. 多仓库出现同名分支时，分支 chip 显示仓庽数。
3. 分支组可展开为多个仓库；每个仓库可独立查看提交。
4. 每条提交详情至少能定位到项目/仓库名，不能只展示 SHA。
5. 未绑定或取数失败的仓库保留可见状态，并显示具体原因。
6. 确认选择一次只回传一个仓库的 SHA 集合，当前提取/扫描链路语义不变。

## 11. 验收返修（2026-11-07）：多仓库指的是同一个工作空间目录

第一轮实现（派生单 T04527）把「多仓库」理解成「多个 MTask 项目、各自绑定各自的工作空间」，验收被打回：
需求原话是「`D:\code\QJ\BEMP5.0DEV` 下有 master 和 feature/hnnxbank/dev 分支，且同目录下有
served/deploy/adapter/banks 等多个仓库」——**仓库维度不是项目维度，一个项目目录里可以住着一堆仓库**。

返修后的口径（本轮实测已覆盖，见下方「证据」）：

1. **仓库身份 = 项目 + 目录内相对路径**：`repoKeyOf(projectId, repoSub)`，`repoSub` 为空串即根仓库。
   旧的「仓库 ≡ 项目」假设会让子仓库与根仓库共用一份提交数，也会让 8 个子仓库把根仓库的展示名顶成「· 目录名」。
2. **仓库根的唯一判据是 `.git` 实体**（`server/src/services/nestedRepos.ts:isRepositoryRoot`），
   刻意不用 `git rev-parse --is-inside-work-tree`：后者对工作树内的任意子目录都返回 true，
   实测会让根仓库里的 `docs/` 冒充子仓库并返回根仓库的历史（D-06 就是这么被抓出来的）。
3. **有界发现**：深度 ≤ 2、最多 40 个仓库、最多扫描 2000 个目录；命中即边界（进了仓库就不再向下钻），
   跳过隐藏目录与 `node_modules`/`dist`/`build`/`out`/`target`/虚拟环境等。
4. **路径不许逃逸**：`resolveRepoSubPath` 用几何相对 + 平台大小写折叠判包含，越界直接拒绝（`bad-repo`），
   **不回落根仓库**——回落等于把「这个仓库没有这条分支」谎报成「这条分支没提交」。
5. **接口契约为此扩了一维**（与 §2 原则 3 的「不改 API」相比是有意的偏离）：
   `GET /git/log` 新增可选 `repoSub` 并在成功响应里回显；新增只读 `GET /git/repos?projectId=` 返回目录内仓库清单。
   不带 `repoSub` 时请求串与改造前逐字节一致，旧调用方零感知。
6. **普查与取数都有上限**：默认只展开「同名仓库数最多的前 `DEFAULT_OPEN_BRANCH_GROUPS=3` 组」，
   且窗口取数只对**已展开的分支组**排队、在途并发 ≤ `REPO_SCAN_CONCURRENCY`。
   这两条是浏览器门逼出来的：8 仓库 × 30 分支组按旧写法一次铺出 216 个 git 取数，弹窗直接卡死。
7. **聚合入口不再看项目个数**：入口条件从 `projects.length > 1` 放开到 `> 0`——只有一个项目时，
   用户同样要能点开聚合视图看同一目录里的多个仓库（这正是被打回的那一屏）。
8. **跨仓库确认仍然拒绝**，并且改为「按钮可点 + 点击后给原因」，而不是给一只没有解释的灰按钮；
   页脚同时如实显示「已选 N 个提交 · M 个仓库（一次只能确认一个仓库）」。

### 已知缺口（不在本轮范围，已建派生单）

- `task_git_links` 的写入与「Git 增量资产提取」仍以**项目工作空间根**解析 SHA（`rev-parse --verify`），
  没有 `repoSub` 这一维：子仓库的提交在关联/提取链路里会被判成 `missing`。视图能看见、能选，
  但选完回写后按根仓库解析会报缺——必须补一维才有闭环。
- 引用清单目前由 `parseRefDecorate` 从提交装饰反推，同名分支的「这仓库到底有没有这条分支」是推断而非事实；
  应改用 `git for-each-ref` 逐仓库直取（已建派生单 T04552）。
- 「同一工作空间多仓库」与既有 `scopeWorkspace` 单工作空间约束的归属关系需要产品裁决（已建派生单 T04553）。

  跨两个仓库勾选时确认被拒并点出仓库数）。
