## 2. 评审结论

1. **范围可批准**：49 条需求全部落在「九个一级菜单 + 设置 + 命令面板 + 移动端核心链路 + AI 工作台」内，无跨产品扩张；§4.2 非目标与需求正文无直接冲突。
2. **口径已自洽**：D-01（任务二元状态）、D-02（迭代落在计划行）、D-03（预测对象分离）、D-04（不伪造金额）、D-05（`card_key` 落库）构成了后续设计的硬约束，解决了两份来源文档的主要矛盾。
3. **可与现有资产对接**：核心能力（任务/计划/需求矩阵/AI 卡/执行会话/用量/主题）在 `server/src` 与 `web/src` 均有落点，本 PRD 以**增强与收口**为主，未出现「要求重写既有机制」的条目。
4. **前置条件 6 条**（不影响批准，设计/实施时必须先满足）：
   - C1 时间口径原语（D-12）必须先于逾期率、燃尽、预测三类展示落地；
   - C2 结构化搜索必须在**后端全集**执行（PM-102 ④⑤），不得在内存前 500 条过滤；
   - C3 `ai_usage.card_key` 与 `prompts.usage_count` 只能幂等加列（D-06），不得改造既有写入路径语义；
   - C4 深链契约（D-13）先于面板/Tab 重构定义路由与锚点；
   - C5 AI 不可用入口统一「可见禁用 + 原因」策略（D-14），三种现状需收敛为组件级规范；
   - C6 导出样式固定浅色（PM-301 ⑦），主题改造不得波及 `server/src/util/exportStyle.ts`。

## 3. 范围边界确认

### 3.1 纳入范围（本期）

- 九个一级页面、设置（14 子页）、命令面板、全局反馈（提示/确认/骨架/空态）的体验整改。
- 项目管理的看板 WIP、迭代、里程碑预测、项目洞察、导出所选、Webhook 外发与脱敏分享快照。
- AI 工作台的生成前预估、分段可靠性、溯源、模板、卡片组织/排序、模型路由、执行会话可观测。
- 移动端任务核心链路 + 需求/计划只读。
- **最小、向后兼容**的数据增量：`ai_usage.card_key`、`prompts.usage_count`（均已落地，见 §5）。

### 3.2 明确排除（本期不做）

多人实时协作/角色权限/组织体系；任务第三状态与任务级截止日；移动端甘特编辑；Issue→写码→PR 的编码代理；真实 token/金额计费；inbound Webhook；既有 RTM/估算/AI 闭环/主题机制的重构；macOS/Linux 打包与完整 i18n。

### 3.3 取舍原则（评审补充，供设计与实施共用）

1. **复用优先**：能扩展既有服务/组件的，不新建平行实现（批量动作与十级撤销、命令面板、主题机制、计划时间线、AI 卡注册表均属此列）。
2. **最小增量**：数据库只做幂等加列/加表，且必须可回退（老库启动不崩）。
3. **口径单源**：同一度量只有一个计算入口（逾期率、J 成功率、覆盖率、预估偏差），前端只渲染不重算。
4. **失败可复盘**：任何批量/生成/外发动作必须留下逐条回执，不允许「部分成功静默丢弃」。

## 6. 风险与待验证（对齐 PRD §9）

1. **数据积累型指标**（逾期率、AI 覆盖率、汇报耗时）初始样本不足 → 视图必须区分「无人使用」与「未接埋点」，不得用 0% 冒充。
2. **时区与边界日**：`end_date` 为纯日期，是否含当日需由统一测试固定（D-12）；跨时区项目必须先配置项目时区。
3. **性能基准可复现性**：5000 条列表与 1000 条搜索需固定数据集与三轮采样，否则结论不可比。
4. **AI 质量类验收**（AI-101/301 等）无法完全自动化 → 结构化输出校验 + 人工抽查清单双轨，verified 诚实标注。

## 7. 对 142 条拆解单的映射与处理顺序

1. **顺序**：按 `task_no` 升序、P0 优先；同一需求族的汇总单（如 §5）在其子单全部完成后收口。
2. **依赖**：C1 时间原语 → 逾期/燃尽/预测；C4 深链契约 → 面板重构；`card_key` 接入 → 覆盖率视图 → 卡片排序。
3. **验证等级**：命令可验证项（编译/接口/数据断言）进验收门；交互与 AI 质量项 verified=false + 人工抽查步骤，不虚标。
4. **去重**：以 §10 追溯矩阵为准，UX 归并需求不再反向拆分出与原编号重复的单。
