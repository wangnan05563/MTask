# T03285 PM-201 迭代路径决策记录（M3 3.1）

> 决策对象：PM-201 迭代（Sprint）管理是否采用「零新表路径」
> 结论：**不采用零新表路径**，采用 2 张新表（`project_iterations`、`iteration_events`）+ 3 个普通索引 + 1 个部分唯一索引
> 约束：无论选择何种实现，迭代行为一律按 D-02「迭代 = 项目下计划行的带时间集合」

## 1. 表达能力验证：零新表为什么不够

| 需要的能力 | 零新表能否表达 | 依据 |
|---|---|---|
| 迭代本体（名称/目标/DoD/起止/状态/归档） | 无法表达 | `plan_tasks` 是计划行，`tasks` 是待办；迭代不是行，需要在行之外挂一组属性，只能塞进 `app_settings` 这类 KV，查询与排序都失去索引 |
| 迭代 ↔ 计划行的多对多成员关系 | 无法表达 | `plan_tasks.parent_id` 是树结构，不表达「同一条计划行先后属于不同迭代」 |
| 成员中途加入/移出留痕（PM-201⑤） | 无法表达 | `task_events` 以待办 id 为键，计划行没有等价的逐行事件流；用「当前在册行」倒推会把燃尽实际线算成猜测，正是本项要消灭的缺陷 |
| 周报卡「补生成且仅一份」 | 无法表达 | 需在库层保证同一迭代至多一条周报卡，KV 文本做不到 |

结论：零新表只能覆盖「一迭代对应一组行」的静态读法，覆盖不了成员变更历史与唯一性约束，故不采用。

## 2. 迁移成本与回滚

- 新增 2 张表：`project_iterations`（迭代本体）、`iteration_events`（成员变更事件流，含周报卡 kind）
- 索引：`idx_iterations_project(project_id, start_date)`、`idx_iteration_events_iter(iteration_id, created_at)`、`idx_iteration_events_task(plan_task_id, created_at)`、部分唯一索引 `uniq_iteration_weekly_card`（仅 `kind='weekly_card'`）
- 全部为**增量加表/加索引**，不改既有列；回滚 = `DROP TABLE` / `DROP INDEX`，无数据迁移不可逆风险（满足 NFR-10）
- 建表在 `server/src/db/schema.ts` 内以 `CREATE TABLE IF NOT EXISTS` 幂等执行，重复启动不会重复建

## 3. D-02 语义落位（实现侧证据）

- 成员就是计划行：`IterationService.attach(id, planTaskIds, mode)` / `detach(id, planTaskIds)` 全程以 `plan_task_id` 为主键维度，不出现任务 id
- 事件流：`iteration_events.kind` 记录 attach/detach，移出时在**原迭代**留痕；燃尽重建按事件回溯，不回写历史
- 周报卡：`iteration_events` 中 `kind='weekly_card'` 由偏唯一索引封顶，`plan_task_id` 置空串
- 燃尽双口径：`IterationService`（PM-201④）按业务日回溯「剩余计划数 / 剩余工期」

代码位置：`server/src/db/schema.ts`（262-292 行）、`server/src/services/IterationService.ts`（成员/事件/燃尽）
