## 3. 组件级功能亮点（从判据里摘出的硬证据）

1. **外链安全**：`t03436` W 组 33 项白名单负例全绿——`git remote add/set-url/remove/prune/update/rename`、`cat-file --batch-command/--batch-all-objects/-e/-t/--textconv/--filters` 全部 `denied`，写类子命令 `push/fetch/checkout/commit/clean/gc/apply/am/rebase/reset` 全不在白名单。
2. **降级不静默**：无 origin → `kind=no-remote`（不是 `failed` 原始报错）；非仓库 → `not-a-repo`；两者不混。
3. **导出并发闸非阻塞**：第 3 个请求 `429` 且不排队，`finish` 后计数归零（G-04），不与周报闸同名（G-05）。
4. **扫描回写护栏**：单次 ≤50 + 1 条汇总；原任务是子任务时挂父 epic，不产生三级；指纹 7 天内不重复建单。
5. **MCP 工具语义**：`mtask_link_git_commit` 一条都没写进去时返回 `isError`（T03350），避免 Agent 把 0 关联当成功。

## 5. `t03367` 首轮 L-11 红：负载噪声，复测转绿

- 首轮（九门串行连跑）：`[FAIL] L-11 单任务集提取走 cat-file 单进程：整轮耗时量级符合 p95≤1.5s 的取数侧前提 :: {"毫秒":2343}`
- 单独复跑：`[PASS] L-11 … :: {"毫秒":1373}`，整门 **PASS=92 FAIL=0**

结论：该判据是**时间阈值型**，在同一台机器上受并发负载影响明显（1.37s 与 2.34s 差 70%）。**建议**：CI/复跑时逐门串行、不与其他压测并行；阈值本身偏紧（1373ms vs 1500ms 余量仅 8%），若要长期稳定，应改为「同机基线相对倍数」而不是绝对毫秒——（仅观察不建单）。

## 3. 不可构造场景（如实声明，不假装已测）

| 场景 | 为什么不可构造 | 现在的替代证据 |
| --- | --- | --- |
| `no-git`（机器上根本没有 git） | 本机 git 是构建链必需，卸载会破坏其它一切 | 分类枚举存在性（`t03436` M-06）+ 注入式单测 |
| 真实 30s 超时 | 门跑一次要等 30s 以上，且不可复现 | 门内注入超时值（`t03376` D-08） |
| 真实 8MB buffer 溢出 / 仓库过大 | 构造真实大仓库成本高、且会拖慢整族门 | 走 kind 分支单测，未做真机溢出 |
| 真实 SonarQube 服务器全链路 | 本机无 Sonar 服务；`t03376`/`t03405` 用假服务器与夹具扫描器 | 接口契约 + SSE 帧序已覆盖；**端到端对真 Sonar 的联调未做** |

以上四类此前已在 T03604 / T03608 挂账，本报告引用其结论而不重复挂单；真机联调需要环境，属「设备/服务就绪后复验」的观察项（仅观察不建单）。

## 4. Sonar 侧

### 4.1 Token 生命周期

```
用户输入 → saveSonarConfig → util/crypto.ts AES-256-GCM 加密 → app_settings
读取（列表/表单）→ maskSecret 脱敏 → 界面
扫描 → 仅经子进程环境变量 SONAR_TOKEN 传入（sonarScan.ts:801）
查看原文 → POST /settings/sonar/reveal（confirm 必须为 true）→ 回明文 + 写审计
```

**关键事实（代码走查）**：

1. `buildProperties()`（`sonarScan.ts:196-211`）**不写 Token**——注释明确「properties 会随快照留在磁盘上，能被打包带走」，Token 改走环境变量。
2. 扫描器 stdout 会回显参数，因此输出逐行过 `redact()`（`sonarScan.ts:215`，掩码形如 `abcd****wxyz`）。
3. 临时 `sonar-project.properties` 与快照目录一起被回收（`t03376` D-10：失败/中止同样回收，不把源码副本留盘）。
4. 审计表 `sonar_reveal_audit` 字段 `revealed_at/actor/target/server_url/ok/note` —— **不含 Token**。

### 4.2 进程调用

`execFile` 不走 shell；配置的扫描器路径先探测存在性（不存在 → `available=false` 并点名路径），避免「路径填错→执行任意程序」的意外面。

### 4.3 采集范围与只读

扫描/导出都基于**提交快照**（`cat-file --batch` 取 blob 到 `MTask_DATA_DIR/tmp`），`.scannerwork` 落在快照目录；被采集仓库全流程 `git status` 不变（`t03376` B 组、`t03367` K 组、`t03436` N 组）。

## 4. 结构与瓶颈分析

1. **列表页不受页大小线性拖累**：徽标数据来自 `GET /tasks` 内联字段 + 一次 `POST /git/commit-summaries`。200 个唯一 SHA 仍是**一次** `git log --no-walk`（656ms 级），页内零逐行请求；60s 页级缓存命中后接近 0。翻页/筛选变化才重取。
2. **抽屉首屏是靠「并发 + 缓存」压进 1.5s 的**（T03642）：串行 881ms → 并发 655ms。5 提交时差异不大，但提交数上升时串行会线性劣化（每提交一次 spawn），并发把斜率摊平。
3. **`cat-file --batch` 是导出/扫描的正确底座**：501 个对象 429ms；若逐文件 `git show`，按单进程 ~120ms 计，501 个文件约 60s——这正是 PRD §3.3.2 禁止逐文件 spawn 的原因，实测差两个数量级。
4. **回写是逐条 spawn**：每条短 SHA 解析 123ms。回写 100 条 ≈ 12s。这个成本可接受（回写是低频动作），但**不要**在批量导入场景里逐条调用。
5. **导出闸/并发闸本身不耗时**：`t03367` G 组与 `t03376` H 组证明第 3 个请求立即 429（不排队），`finish` 后计数归零，无泄漏。

4. **导出/扫描的临时产物**写入应用数据目录 `tmp/`，下载即删或 6 小时后清理；不写入被采集仓库。
