# MTask CSRF 防护方案设计（M8 / 8.1）

> 日期：2026-10-01
> 背景：server 域全面评审遗留 P1——CSRF 为系统性既有问题。经查仓内**无任何 CSRF 实现**（`grep -i csrf` 零命中），缺口确认真实。
> 目标：给出可落地的选型、豁免边界与验证口径，供 8.2（服务端中间件）/ 8.3（前端改造）实施。

---

## 1. 威胁模型（先界定要防什么）

MTask 后端是 **本机回环服务**（`127.0.0.1:39877`）+ 可选 tunnel 公网可达。攻击面是：
**受害者在浏览器登录/开着 MTask 页面时，被诱导访问恶意站点，该站点对本机或隧道地址发起跨站请求**。

关键前提：
- 现有鉴权是 **自定义头 `X-Access-Token`**（`accessTokenGuard`），**不是 Cookie**。
- 浏览器**不会**自动携带自定义头；跨站表单/`<img>`/`fetch` 也无法让浏览器自动附加自定义头。
- 因此：**纯自定义头鉴权的写入接口，天然免疫 CSRF**（这是本方案最重要的结论）。

真正的风险点只有两处：
1. **tunnel 场景下的 Cookie 会话**：若 tunnel 子路径下浏览器持有 Cookie/Session 并自动携带 → 存在 CSRF 面。
2. **简单请求（simple request）**：若将来引入 Cookie 鉴权或表单提交（`application/x-www-form-urlencoded`），跨站可无预检直接发出。

---

## 2. 选型结论（推荐：自定义头强制 + 双提交 Cookie 兜底）

| 方案 | 评价 | 结论 |
|---|---|---|
| **A. 强制自定义头（现状加固）** | 浏览器跨站无法自动附加自定义头，等价于事实上的 CSRF 防护；零改造成本 | **采纳（主线）** |
| B. 双提交 Cookie（Double Submit） | 读 Cookie 写头，同源策略保证跨站读不到 | 采纳（**tunnel/Cookie 场景兜底**） |
| C. Synchronizer Token（服务端下发 token 表单） | 最严谨，但需全站表单改造、SPA 成本高 | 不采纳（收益/成本不划算） |
| D. 仅校验 Origin/Referer | 有代理/隐私策略下 Referer 缺失问题 | 作为**辅助校验**，不单独依赖 |

**推荐组合**：主线 A（强制 `X-Access-Token` 自定义头，服务端拒绝无头请求）+ tunnel 场景 B（双提交）+ 全场景 D 的 Origin 校验作为辅助。

---

## 3. 豁免范围（明确不拦）

以下**必须豁免**，否则会打断既有链路：

| 路径 | 原因 |
|---|---|
| `GET /api/health` | 启动探针 / 监控；只读且无副作用 |
| **MCP 端点（`/mcp` 或 MCP over HTTP）** | MCP 走独立鉴权（api_tokens / 会话），不属于浏览器跨站面 |
| tunnel 的 SSE / 图片直链 | 已在 T01420 修正 `originalUrl` 前缀剥离后再鉴权；SSE 是 GET 长连接，仅放行只读 |
| 静态资源（`web/dist`） | 无状态副作用 |

> ⚠ 豁免只允许 **安全方法（GET/HEAD/OPTIONS）** 或上述明确端点；**任何状态变更方法（POST/PUT/PATCH/DELETE）一律不豁免**。

---

## 4. 服务端落地要点（8.2 实施依据）

1. 中间件顺序：置于 `accessTokenGuard` **之后**、业务路由之前；先判豁免，再校验。
2. 校验顺序：`Origin`（若在白名单内放行）→ 自定义头存在性 → （tunnel/Cookie 场景）双提交比对。
3. 失败响应：**403 + 明确错误码**，不要 401（避免与鉴权失败混淆），并记录审计日志（含 UA/Origin）。
4. 隧道子路径：必须基于 **剥离前缀后的 `originalUrl`** 判定路径与豁免（沿用 T01420 已有修正，勿用 `req.url`）。
5. 配置开关：提供 `MTASK_CSRF_MODE=off|header|double-submit`，默认 `header`，便于临时排障与灰度。

---

## 5. 前端改造要点（8.3 实施依据）

- `web/src/api.ts` 统一注入 `X-Access-Token`（现状已有）——**确认所有写请求都走该封装**，不允许散落的裸 `fetch`。
- 如启用双提交：读 `document.cookie` 中的 `mtask_csrf`，写入 `X-CSRF-Token` 头。
- 移动端（MobileXxx）与桌面共用同一封装，需一并回归。
- SSE/EventSource 无法自定义头 → 依赖 tunnel 场景的 Cookie 双提交或 query token，需单独设计（不阻断本次）。

## 7. 风险与遗留

- 本机回环场景下 CSRF 风险本身较低（攻击者需诱导本机浏览器），但 tunnel 公网可达会放大，**必须**在 tunnel 场景落地双提交。
- SSE 与图片直链无法带自定义头，需单独方案（建议 tunnel 侧短期 token）。
- 开启严格模式前需确认所有内部调用方（Electron 主进程代理、MCP、脚本）都已带合规头，否则会大面积 403。
