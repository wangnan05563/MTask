# T03305 代码评审讲稿：补充大纲内容（逐项目/逐模块讲解）分段生成方案

> 交付物：可直接指导编码的优化设计（本单不改代码）。面向现场报错：110 文件、+1236/-8552 的变更集下，
> 「逐项目-逐模块讲解」出现 1 条输出截断 + 2 条 60s 连接超时。

## 1. 问题分析

### 1.1 现场证据（工单截图）

同一节（`walkthrough`）三个分组：

| 分组 | 报错 |
| --- | --- |
| `mtask六期 / docs` | AI 输出超长被截断（已输出 3549 字符） |
| `mtask六期 / server/src/services` | 连接超时（超过 60000ms） |
| `mtask六期 / web/src/pages` | 连接超时（超过 60000ms） |

### 1.2 现状不是「一次性请求全部项目」，而是「每次仍按项目×模块整包」

读代码可见现有实现已经是多次调用：

- `server/src/services/lectureStream.ts:482-540`：八段逐段循环，段内 `for (const unit of units)`，每个 unit 一次 `generateLectureSection`（`groups: [unit]`）。
- `server/src/services/lectureStream.ts:257-277`：`walkthrough` 的 unit = `context.groups`，即「项目 × 模块」一组。
- `server/src/services/lectureService.ts:534-585`：一次 `askStream` 只为当前组生成。

所以报错并不是「一次装了所有项目和模块」，而是**单组本身仍然太大**：

1. **输入侧过大 → 超时**：`lectureContext.ts:28` 的组预算 `LECTURE_CONTEXT_BUDGET = 60_000` 字符；
   一个模块（如 `server/src/services`）可以合法吃满 60k 字符。60k 字符（≈3 万 token）预填 + 生成，
   在 60s（工具配置 `timeoutMs` 默认 60000，见 `aiService.ts` 中 `config.timeoutMs ?? 60000`）里跑不完。
   `buildUnits` 对 `risks/standards/improvements` 更是把**该项目全部模块**合并后截断（`lectureStream.ts:279-295`），
   跨项目汇总节甚至把所有项目合一份（`lectureStream.ts:297-310`）——这几节天然更容易超时。
2. **输出侧过长 → 截断**：`docs` 组只输出 3549 字符就被判截断，说明该工具 `max_tokens` 偏小
   （截断文案来自 `server/src/adapters/types.ts:118`）。模块越大，模型越容易一次写爆输出上限。
3. **失败粒度粗**：任何一组失败，只保留一条 `error` 字符串（`lectureService.ts:582`），
   既不能只重试失败部分，也无法在成稿里精确标注「哪一块没生成」。

### 1.3 结论

需要的是**在现有「段 → 项目×模块」之下再加一级「组内切片」**，并把「输入超时」与「输出截断」分开治理：

- 输入侧：把一组按文件/按 hunk 切成若干 chunk，单 chunk 目标 ≤ 20k 字符，让每次预填在 60s 内有富余；
- 输出侧：chunk 本身天然更短，输出长度随之下降；若仍有截断，启用「续写」二段式兜底；
- 失败侧：失败只落在 chunk，重试只重试该 chunk，成稿按顺序合并并在失败处留痕。

## 2. 拆分策略

### 2.1 三级粒度

| 级别 | 单位 | 现状 | 本次方案 |
| --- | --- | --- | --- |
| L0 | 八段（opening…closing） | 已逐段 | 不变 |
| L1 | 项目 × 模块 | 已逐组（每模块一组或按 60k 拆多组） | 不变（保留现有分组语义） |
| **L2** | **组内切片 chunk** | 无 | **新增：按文件装箱，单 chunk ≤ 20k 字符且 ≤ 8 文件** |

L2 只处理「仍然过大或已知易爆」的情况，默认不改变小项目的调用次数（小项目 1 组 → 1 chunk，零额外开销）。

### 2.2 切片规则（输入侧）

1. 以组内 `files` 为装箱单位，按当前顺序（模块内已有排序）累加 `content` 片段，超过 `LECTURE_CALL_BUDGET`（默认 20_000 字符）前收口；
2. 单个文件自身超过预算时，用现有 `trimMiddle()`（`lectureContext.ts:178`）保头保尾，并在该 chunk 上记 `trimmed` 警告——不把一个文件拆成两 chunk，否则锚点可用行会跨调用；
3. chunk 必须携带**本 chunk 可见的锚点行集合**（`files` 里的 `hunk` 行号），prompt 里的【可用锚点行】只放本 chunk 的行（沿用 `buildSectionPrompt` 的现有字段），保证模型引用的锚点一定在本次上下文里；
4. chunk 数上限保护：单组最多 8 个 chunk，超出则合并尾块并记警告（防止 200 个小文件把调用数打爆）。

### 2.3 输出侧

- **A（首选）**：chunk 天然更短，输出随之变短；给 `askStream` 显式传 `maxTokens`（取工具配置与「本 chunk 预期输出」的较小者，最小 2048），避免工具配置过小。
- **B（兜底）**：若某 chunk 仍报「输出超长被截断」，对该 chunk 发起 1 次**续写调用**：附上已输出文本的末尾 400 字符 + 「接着上文继续，不要重复已写内容，从上次中断处继续」，拼接结果。续写最多 1 次（避免无限接力），仍失败则按 partial 记录。
- 续写只对 walkthrough 这类「长描述」段启用；`risks/standards/improvements/questions` 保持单次。

## 3. 调用流程设计

```
for section in 八段:                       # 不变
  units = buildUnits(section)              # 不变（项目×模块）
  for unit in units:                       # 不变
    chunks = splitUnitForCalls(unit)       # 新增 L2 切片（默认 1 个）
    parts = []
    for i, chunk in enumerate(chunks):
        emit stage { section, unit, chunkIndex: i, chunks: len }   # 进度只增字段
        run = askStream(buildSectionPrompt(section, chunk), timeout=perCallTimeout)
        if !run.ok and isTruncated(run.error) and section==='walkthrough':
            run = continueCall(run)        # 输出侧兜底 B
        if !run.ok and isTimeout(run.error):
            run = askStream(buildSectionPrompt(section, chunk.shrink(0.5)), timeout=perCallTimeout*1.5)  # 只重试该 chunk，输入减半
        parts.append({ chunk, run })
    segment = mergeChunks(parts)           # 按 chunk 顺序拼接，失败 chunk 记 notGenerated
```

要点：

- **参数传递**：每个 chunk 的 prompt 共享同一份 `section`（大纲里的 title/bullets）、同一份 `outline`、同一 `style/extraNote`，只替换 `group.content` 与 `files`；
  即「上下文一致、输入分片」，避免各 chunk 语气分裂。
- **结果合并**：段内按 `(projectName, module, chunkIndex)` 顺序拼接，chunk 之间加小标题 `#### 模块 X（续 k/n）` 仅在 n>1 时出现；
  段末保留现有「⚠️ 本节部分内容未生成：…」留痕（`lectureStream.ts:547-549`），改成按 chunk 粒度列出。
- **进度**：`segment_done` 事件保持原字段，新增 `chunkIndex/chunks/totalChunks`；
  `progress` 仍按八段推进，chunk 只影响当前段的文本进度提示（`3/7 段 · 模块 server/src/services（chunk 2/3）`）。
- **中止**：沿用 `signal`，在 chunk 循环入口与每次 await 后检查，行为与现在一致（已生成 chunk 保留）。
- **单节重试/续作**：`sectionKeys` / `resumeFrom` 语义不变；chunk 结果只存在本次 run 内存里，
  跨会话续作仍按「节」粒度重新生成整节（若需要 chunk 级断点，另开单做持久化，不在本方案范围）。

## 4. 注意事项

1. **锚点可用行必须按 chunk 收窄**：`validateLectureAnchors(text, chunk.files)` 只能用本 chunk 的文件集合校验；
   prompt 里的【可用锚点行】同样只能列本 chunk 的行——否则模型会引用未发送的 hunk，触发「落点存疑」告警。
2. **`stats.calls` 语义会变**：现在等于「组数」，切片后等于「chunk 调用数」。AI 控制台与成功率统计（T03192）都读它，
   落地时必须同步文案（例如「AI 调用 27 次」），并在门里断言「小于等于 chunk 上限」而不是「等于组数」。
3. **总耗时**：切片增加调用次数，wall time 可能上升（并行会打爆工具并发与额度，**不建议**默认并发；
   若要做并发，最多 2 路且只对同一段的 chunk，且工具声明支持并发）。
4. **超时预算**：per-call timeout 建议取 `max(工具 timeoutMs, 90s)`，但不要无限放大——90s 仍超时说明输入还是太大，
   应走「输入减半重试」而不是继续等。
5. **部分失败必须可见**：chunk 失败不能静默丢，成稿段末要点名 `项目/模块（chunk 2/3）：原因`，与现有 partial 口径一致。
6. **向后兼容**：只增事件字段，不改 `LectureStreamResult` 既有结构；`sections[].segments[]` 由「组」变成「chunk」，
   UI 只消费 `heading/ok/text`，需要把 heading 里补上 chunk 序号（n>1 时），避免同模块多条 heading 重复。
7. **空变更上下文**：`manifestText` 为空仍应在最外层拦住（现有 `outlineLecture` 已拦），切片函数不承担该判断。

## 5. 代码/伪代码示例

### 5.1 切片函数（新增，建议放 `server/src/services/lectureContext.ts`）

```ts
export const LECTURE_CALL_BUDGET = 20_000;   // 单次调用上限（字符），可用 MTASK_LECTURE_CALL_BUDGET 覆盖
const MAX_CHUNKS_PER_UNIT = 8;

export interface SectionUnitChunk {
  index: number;
  total: number;
  content: string;
  files: readonly GitFileChange[];
  trimmed: string[];
}

/** 单文件摘要复用 lectureContext.summarizeFile(project, file)：组里的 content 是拼好的整串，
 *  按文件重切必须从 file 列表重新摘要（不能按字符位置切字符串，否则 hunk 头会被切碎） */
export function splitUnitForCalls(
  project: LectureContextProject,
  unit: { content: string; files: readonly GitFileChange[] },
  budget = Number(process.env.MTASK_LECTURE_CALL_BUDGET) || LECTURE_CALL_BUDGET,
): SectionUnitChunk[] {
  if (unit.content.length <= budget && unit.files.length <= 8) {
    return [{ index: 0, total: 1, content: unit.content, files: unit.files, trimmed: [] }];
  }
  const chunks: Array<{ content: string; files: GitFileChange[]; trimmed: string[] }> = [];
  let cur = { content: '', files: [] as GitFileChange[], trimmed: [] as string[] };
  for (const file of unit.files) {
    const text = summarizeFile(project, file).text;      // 复用现有单文件摘要（含 hunk 行）
    if (text.length > budget) {
      const { text: cut, truncated } = trimMiddle(text, budget, `文件 ${file.path}`);
      if (truncated) cur.trimmed.push(file.path);
      cur.content += (cur.content ? '\n\n' : '') + cut;
      cur.files.push(file);
      continue;
    }
    if (cur.content.length + text.length + 2 > budget) {
      chunks.push(cur);
      if (chunks.length >= MAX_CHUNKS_PER_UNIT - 1) {
        // 尾块合并，避免文件数过多把调用数打爆
        cur = { content: '', files: [], trimmed: [] };
        break;
      }
      cur = { content: '', files: [], trimmed: [] };
    }
    cur.content += (cur.content ? '\n\n' : '') + text;
    cur.files.push(file);
  }
  if (cur.content || cur.files.length) chunks.push(cur);
  const rest = unit.files.slice(chunks.reduce((n, c) => n + c.files.length, 0));
  if (rest.length) {                                     // 超上限的尾块并进最后一个 chunk（保头保尾截断）
    const last = chunks[chunks.length - 1];
    const joined = rest.map((f) => summarizeFile(f).text).join('\n\n');
    const { text } = trimMiddle(`${last.content}\n\n${joined}`, budget * 2, '尾部文件');
    last.content = text;
    last.files.push(...rest);
    last.trimmed.push(...rest.map((f) => f.path));
  }
  return chunks.map((c, i) => ({ ...c, index: i, total: chunks.length }));
}
```

### 5.2 调用侧（改 `lectureStream.ts` 的 unit 内循环）

```ts
for (const unit of units) {
  if (signal?.aborted) { aborted = true; break; }
  const chunks = splitUnitForCalls(projectOf(unit.projectId), unit, callBudget);   // projectOf: usable 里按 id 取
  const parts: LectureSegmentResult[] = [];
  for (const chunk of chunks) {
    if (signal?.aborted) { aborted = true; break; }
    hooks.onStage?.({
      phase: sectionPhase(index),
      msg: `装配「${unit.projectName}/${unit.module}」${chunks.length > 1 ? `（${chunk.index + 1}/${chunk.total}）` : ''}`,
      progress: sectionStartProgress(index),
      data: { type: 'chunk_start', section: meta.key, projectId: unit.projectId,
        module: unit.module, chunkIndex: chunk.index, chunks: chunk.total },
    });
    let run = await askChunk(toolId, section, outline, unit, chunk, perCallTimeout, signal);   // 内部等价 generateLectureSection 单组逻辑
    if (!run.ok && isTruncated(run.error) && meta.key === 'walkthrough') {
      run = await continueChunk(toolId, section, outline, unit, chunk, run.text, signal);      // 输出侧兜底
    }
    if (!run.ok && isTimeout(run.error)) {
      const half = { ...chunk, content: chunk.content.slice(0, Math.ceil(chunk.content.length / 2)) };
      run = await askChunk(toolId, section, outline, unit, half, Math.round(perCallTimeout * 1.5), signal);
    }
    stats.calls += 1;
    parts.push(toSegment(unit, chunk, run));
    hooks.onStage?.({ /* segment_done，字段同现状 + chunkIndex/chunks */ });
  }
  // 合并：按 chunk 顺序；失败 chunk 保留「未生成」标记
  const seg = mergeChunkParts(unit, parts);
}
```

## 6. 方案对比与推荐

| 方案 | 做法 | 稳定性 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| A 输入侧切片（本文 §2.2） | 组内按文件装箱，单次 ≤20k 字符 | 高（直接消除 60s 超时根因） | 调用数增加（大模块 3~4 倍） | **推荐作为主方案** |
| B 输出侧续写 | 截断后追加一次续写 | 中（依赖模型遵守勿重复） | 少量额外调用 | 作为 A 的兜底，仅 walkthrough |
| C 调大 max_tokens / 换大模型 / 放宽 timeout | 改工具配置 | 低（同类变更量变大仍会复发） | 零代码 | 仅作为运维临时缓解，写入报错文案建议 |

推荐组合：**A 为主 + B 兜底 + C 仅文案建议**。这样「110 文件、-8552 行」这一量级下，
单次调用的输入与输出都被压到可控区间，失败被限制在 chunk 级，且小范围评审（1~2 个文件）调用次数不增加。

## 7. 落地验收建议（供实现单使用）

1. `scripts/tests/verify-t02872-lecture-diff-ui.mts` 的桩服增加两条能力：模拟「输出截断」与「单次调用 >60s 超时」，
   断言：① 大模块被切成 ≥2 chunk（`chunk_start` 事件数与 `stats.calls` 一致）；② 某个 chunk 首轮截断后触发续写并成功拼接；
   ③ 某个 chunk 超时后按减半输入重试成功；④ 全部失败时成稿段末逐 chunk 点名。
2. 小范围回归：1 个项目 1 个模块时 `stats.calls` 与改造前逐字相等（证明没有无条件增加调用）。
3. 锚点门：每个 chunk 引用锚点必须落在本 chunk 的 `files` 内（把现有 `validateLectureAnchors` 的入参固化为 chunk.files 后自动成立）。
