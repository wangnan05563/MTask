2. 背景与目标

2.1 背景

MTask 已具备「PRD 导入 → 需求跟踪矩阵 → 计划/待办 → 外部 Agent 执行 → 执行会话观测」的完整链路，但测试侧仍是断点：

  1. 测试资产分散：手工用例在「测试用例视图」，UI 自动化脚本散落在各仓库，AI 测试任务靠人手写提示词，三者互不关联。
  2. 没有产品级测试地图：系统不知道产品有多少菜单、页面、功能点，哪些已被测试覆盖，哪些从未被验证，覆盖率不可度量。
  3. 测试任务拆分靠人：面对一次版本迭代，人工判断「测哪里、拆多细、派给谁」效率低且不一致，容易漏测。
  4. 执行过程是黑盒：外部 Agent 执行 UI 测试时，进度、阶段、失败步骤、截图证据无法在 MTask 内实时看到。
  5. 没有闭环：测试失败后缺陷登记、修复、回归、再测试依赖人工串联；代码变更后也无法自动判断哪些测试需要重跑。

「测试」菜单要把这条链路补成闭环：分析地图 → 拆分任务 → 草稿审查 → 派发执行 → 实时监控 → 缺陷闭环 → 增量再拆分。

编号目标衡量方式（验收口径）

G8顶层按「项目 / 产品」两个互斥维度切换，测试模块全部数据随维度动态切换同一时刻仅一个维度生效；切换后看板、地图、草稿、任务、运行、监控的统计与列表口径一致；无需进入页面内二次选择范围
G9测试资产随项目生命周期归档并可恢复项目沉淀为历史资产后测试数据只读；历史快照归档删除后进入「归档 → 测试资产」sheet；恢复项目时测试数据一并恢复；彻底删除仅删除测试资产

MTask 当前以单用户/小团队自用为主，角色是逻辑角色：默认 test.rbacEnabled=0 时，项目 owner 拥有全部角色；启用 RBAC 后按下表分配。

3.2 核心使用场景

S1 首次建立产品测试地图（PM/QA Lead）

  • 前置：项目已绑定工作空间（projects.workspace_path），代码可读；项目已绑定 product_key（跨项目产品级地图需要）。
  • 主流程：进入「测试 → 测试地图」→ 选择产品/项目范围 → 点击「AI 分析」→ 查看分析进度（阶段、已扫描文件、已识别节点）→ 生成草稿地图 → 人工校正（改名/合并/废弃）→ 发布版本。
  • 异常：工作空间不可读 → 提示配置路径；分析超时 → 保留中间结果并可续跑；AI 输出无法解析 → 降级为「仅静态解析」并标注缺口。

S2 评审并确认测试任务草稿（QA Lead）

  • 前置：存在已发布地图版本。
  • 主流程：进入「测试任务」→ 新建拆分（全量/增量、菜单/页面/功能点、目标项目）→ AI 生成草稿 → 表格审查（勾选、编辑标题/描述/优先级、驳回并填原因）→ 批量确认 → 系统在目标项目创建待办并打「测试」标签（即「派发到任务菜单」，P0 范围；自动指派 Agent 为 P2「自动派发」，见附录 B）→ 展示任务编号清单。
  • 异常：同名任务已存在 → 按 dedupe_key 跳过并标「已存在」；目标项目无权限 → 整批预检失败，不落半批。

S3 外部 Agent 执行并回写监控（AI Agent + QA Lead）

  • 前置：任务已确认并处于 todo；Agent 持有带 test:read/write scope 的 Token。
  • 主流程：Agent 调 mtask_test_list_ready → mtask_test_claim 领取 → 拉取上下文 → 执行 → 周期上报进度 → 逐步回写步骤/断言/截图 → mtask_test_finish_run 收口 → MTask 写 run 终态、更新 test_task_meta 汇总与节点健康度，刷新监控视图（tasks.status 不因运行失败而变更；仅当 run_policy.auto_complete_on_pass=true 且质量门通过时自动置 done）→ QA 在看板查看。
  • 异常：租约到期 → 运行置 blocked；重复领取 → 409；证据超限 → 413。

S4 版本迭代后的增量派生（PM/QA Lead）

  • 前置：已有发布地图 + 基线 commit；代码已合并到工作空间。
  • 主流程：进入「测试任务」→ 点击「增量分析」→ 系统 diff 出受影响节点 → 生成增量草稿（默认只勾选受影响且无开放任务的节点）→ 审查确认 → 生成任务。
  • 异常：结构变更超过阈值 → 推荐全量并说明原因；用户可强制增量。

S5 失败闭环：缺陷 → 修复 → 回归（QA + Dev）

  • 前置：运行失败且存在失败断言。
  • 主流程：监控页点击「生成缺陷」→ 填写严重级别/复现步骤 → 自动在目标项目创建缺陷任务并关联 test_issues → 开发修复并回写 → QA 触发回归运行 → 通过后缺陷置 verified、节点转绿。
  • 异常：缺陷任务被关闭但回归未跑 → 节点保持红色并提示「待回归」。

S6 质量周报（PM）

  • 主流程：测试看板按周聚合：覆盖率、通过率、FPR、失败 Top、Flaky Top、缺陷 MTTR、成本 → 一键导出 Markdown/PDF（复用报表导出能力）。

4.2 模块定位与信息架构

定位：新增一级导航「测试」，位于「项目」与「AI 控制台」之间。

  1. 测试地图是产品维度资产（可跨项目聚合），放进项目内二级页签会导致「同一产品多项目各建一份地图」，无法形成产品级覆盖率。

  3. 执行会话、监督器已在 AI 控制台，测试运行需要引用会话与 Run，但不应把测试业务塞进 AI 控制台，避免概念混淆。

  1. 工作空间发现：项目级分析读取当前项目 workspace_path；产品级地图不重新扫描工作空间，按 §4.11.2 对同 product_key 下活跃项目的 active 项目地图做确定性 rollup（P0 只读预览，P1 可发布）。解析嵌套仓库（复用 nestedRepos 逻辑），排除 node_modules、dist、release、.git。
  2. 静态解析：
    • 导航：解析 NAV_GROUPS 常量（label、tabs、defaultTab），生成 menu 节点（一级）与 menu 节点（二级页签）。
    • 路由：解析 TABS 或 router 配置，生成 page 节点；page.route 取路由 path，page.source_refs 记录页面文件。
    • 功能点：解析页面组件中的交互元素（button、input、select、dialog 触发器、菜单项），生成候选 function 节点；用 i18n key 或可见文案命名。
  3. 指纹计算：

```
fingerprint = sha1(
route path + component export name +
sorted(visible text/i18n keys) +
sorted(interactive element roles/names) +
source file content hash
)
```
node_code（跨版本稳定标识）的生成规则见 §4.3.5；指纹变化只影响 fingerprint，不改变 node_code。

  1. AI 语义补全：按页面分批（每批 ≤ 20 个页面），输入结构化摘要（路由、标题、元素清单、i18n key），不传整份源码；要求输出 JSON 数组。模型输出必须通过 JSON Schema 校验，失败重试 1 次后降级为机械命名。
  2. 能力图归并：把跨页面的功能点归并为 capability 节点（例如「PRD 导入」「工作量评估」「任务派发」），边类型 covers 指向页面/功能点；归并要求至少 2 个证据节点，否则不建 capability。
  3. 校验与打分：confidence 由证据数量、路由匹配、AI 一致票数加权；< 0.6 标 needs_review。
  4. 版本落库：test_maps 记录版本、基线 commit、节点统计、覆盖率快照；节点/边写入 test_map_nodes / test_map_edges。
  5. 人工校正：仅 draft 版本可编辑（published / stale / archived 只读，PATCH 返回 TEST_409_MAP_IMMUTABLE；stale 的修正走「重新分析 → 新草稿」）；地图页支持改名、合并、拆分、废弃、手动新增；人工修改写 origin='manual'，后续重分析按 §4.3.5 继承，以人工值为准（不覆盖，只提示差异）。
  6. 发布（事务）：BEGIN IMMEDIATE → 校验本版本 status='draft' → 同 scope_key 旧 is_active=1 行置 is_active=0, status='archived' → 本版本 status='published', is_active=1, published_at=now → 写审计 → 提交；任一步失败整体回滚。部分唯一索引 idx_test_maps_active(scope_key) WHERE is_active=1 兜底，并发发布只会有一个成功（另一个返回 409 TEST_409_MAP_ACTIVE_EXISTS）。所有读取（覆盖率、拆分、任务、监控、导出、增量基线）统一以 is_active=1 为准，禁止用 ORDER BY published_at DESC 推断。

4.3.5 node_code 生成规则与跨版本继承（P1-06）

dedupe_key 与增量 diff 都依赖 node_code，因此它必须跨版本稳定、改名不变。

生成规则（按层级）

层级规则（按顺序取第一个可用）示例
menu（一级）menu:{navGroupKey}menu:project
menu（二级页签）menu:{navGroupKey}.{tabKey}menu:project.plan
pagepage:{tabKey}；无 Tab key 时 page:{normalize(route)}；仍无 → page:{sha1(sorted source_refs)[:10]}page:plan
functionfn:{pageCode}:{semanticKey}；semanticKey 优先 i18n key，其次 {role}:{normalize(visibleText)}，再次 {role}:{ordinal}；人工新增 → fn:{pageCode}:manual:{uuid8}fn:plan:btn.pert.estimate

normalize()：去首尾空白、转小写、空白与标点折叠为 -、全角转半角。node_code 落库后不可修改，唯一索引 (map_id, code) 保证同版本内唯一。

重分析时的继承（匹配顺序，命中即停）

  1. route 相同 且 source_refs 有交集 → 继承 code。
  2. source_refs 有交集 → 继承 code。
  3. 父节点 code 相同 且 normalize(title) 相同 → 继承 code。
  4. 都未命中 → 视为新节点，按生成规则新建 code，status='new'。

改名只改 title，不改 code；因此改名节点在增量 diff 中不会被误判为新节点，dedupe_key 也保持不变。

人工校正的继承与冲突裁决

  • origin='manual' 的节点及其人工字段（title / description / 合并目标 / 废弃）在新版本中按 code 继承，origin 保持 manual。
  • 新版本 AI 结果与人工值冲突（例如 AI 又给出了被人工废弃的节点）→ 保留人工值，节点标 needs_review（confidence < 0.6 同口径），并写审计 map.manual_override_conflict。
  • 合并 / 废弃写入 test_map_node_tombstones(scope_key, code, reason, replaced_by)；重分析命中墓碑时直接标 status='deprecated'、不入草稿、不生成任务。
  • 拆分（一变多）= 保留原 code 给主节点，其余按人工新增生成 manual: 编码，并在审计 detail 中记录 split_from。

验收口径：对已发布 v1 做人工改名 / 合并 / 废弃后重分析得到 v2，改名节点 code 不变，被合并 / 废弃节点不复活，增量 diff 不把改名节点列为新增（AC-32）。

增量影响面算法（可执行伪代码）

text
输入: baseCommit, headCommit, activeMap, fullThreshold=0.3
1. changedFiles = git diff --name-only baseCommit..headCommit（全部子仓库合并）
2. changedRoutes = 路由表 diff（新增/删除/改 path）
3. changedSymbols = AST diff（导出组件/函数/常量）
4. directNodes = 节点满足任一:
     source_refs 命中 changedFiles
     或 route 命中 changedRoutes
     或 fingerprint 变化
5. affected = directNodes
     ∪ ancestors(directNodes)            // 菜单/页面导航冒烟必须带上
     ∪ sharedComponentDependents(directNodes)  // 共享组件被多个页面引用时全部标记
6. ratio = |affected| / |activeNodes|
7. if navChangedRatio >= 0.10 or ratio >= fullThreshold:
       recommend = FULL，返回原因与受影响节点清单
   else:
       recommend = INCREMENTAL
8. 增量条目过滤:
     仅保留 affected 中 status=active 的节点
     跳过已有开放测试任务（todo/running/waiting）的节点
     跳过 fingerprint 未变且最近 regressionWindow=7 天内已通过的节点
     新节点（status=new）始终保留
9. 输出草稿（默认只勾选前 8 步保留的节点，用户可全选）

增量准确性反馈：

  • 草稿条目被驳回时必填原因（误报/已覆盖/优先级低/其他）。
  • 误报 计入增量误报率；未覆盖但未识别 由人工手动新增，计入漏报。
  • 每次增量提交后写 test_audit_logs，供后续调阈值。

4.4.4 去重规则

dedupe_key = sha1(normalize(node_code) + '|' + granularity + '|' + target_project_id)

  • 跨草稿唯一由 test_task_dedupe(dedupe_key PRIMARY KEY) 承担：该表只保存开放任务（tasks.status='todo' 且未归档）的占用；test_draft_items(draft_id, dedupe_key) 唯一索引仅负责草稿内去重。
  • 去重键不含 map_scope（v1.2 修订）：产品级地图 rollup 与项目级地图使用同一 node_code、同一目标项目、同一粒度时，必须命中同一个去重键，避免「产品维度拆分一次、项目维度再拆分一次」产生重复任务。test_task_dedupe.map_scope / product_key 仅作审计与报表列，不参与主键计算。
  • 目标项目决定产品归属：产品维度拆分时，条目必须先解析 target_project_id；默认取节点变体所属项目，允许人工改到同产品下的其他项目，但改到不包含该节点的项目时预检给出 TEST_422_NODE_NOT_IN_PROJECT 警告并要求确认。
  • 生成草稿时：dedupe_key 命中 test_task_dedupe → 条目标「已存在（Txxxxx）」，默认不勾选；产品维度与项目维度共用同一张占用表。
  • 确认时：事务内 INSERT INTO test_task_dedupe 主键冲突 → 该条置 skipped（原因「并发草稿已创建 Txxxxx」），不建任务。
  • 任务 done / 归档 / 删除时释放占用（DELETE FROM test_task_dedupe WHERE task_id=?），之后同键可再生成。
  • 任务已完成但节点 fingerprint 变化 → 允许重新生成，dedupe_key 追加 fingerprint 短哈希。
  • 同一节点在菜单级已建任务，页面级仍可建（粒度不同，dedupe_key 不同），但 UI 提示「该节点已有菜单级任务，建议等待其完成」。

    • confirmed → 直接返回 result_json 中的已创建清单（幂等重放，不重复建任务）；
    • 非 reviewing → TEST_422_STATE。
  3. 逐条：INSERT INTO test_task_dedupe(dedupe_key, task_id, …)（主键冲突 → 该条 skipped，不建任务）→ TaskService.create（标题、描述、优先级、项目、due_date 可空）→ 写 task_tags（测试、UI自动化）→ 写 test_task_meta（draft_item_id、node_id、map_id、granularity、acceptance_json、dedupe_key）→ 回填 test_draft_items.task_id、status='task_created'。
  4. 全部成功 → test_drafts.status='confirmed'，result_json 写入任务编号清单；任一条失败 → 该条 failed 并回滚该条的 dedupe 占用，其余继续，草稿保持 reviewing 并展示失败原因，支持重试。
  5. HTTP 层支持可选 Idempotency-Key 头：同键重复请求返回首次结果（24h 内），用于客户端重试；没有该头时以上述草稿状态机保证幂等。
  6. 确认后自动把草稿条目对应的地图节点标记 has_task=1（派生字段，可由查询计算，也可冗余加速）。

草稿页交互要求

  • 表格列：勾选、节点路径、标题（可编辑）、粒度、优先级（可改）、目标项目（可改）、复杂度、状态（含 skipped）、去重提示、驳回原因。
  • 顶部：范围（产品/项目）、地图版本、粒度、全量/增量、目标项目、搜索。
  • 底部批量条：已选 N 条、全选/反选、批量优先级、批量项目、确认生成、导出草稿 CSV。
  • 空态：无地图 → 引导去「测试地图」；无节点 → 提示调整粒度或全量/增量。
  • 危险操作：放弃草稿需二次确认；确认生成需展示「将创建 N 个任务到 X 项目」摘要。

缺陷密度open 缺陷数 / 100 个 active function 节点P2/P3 也计入当前

平均耗时P50(duration_ms)、P90(duration_ms)仅成功/失败终态周期
成本SUM(tokens)、SUM(cost)；每通过用例成本 = cost / passed_cases无成本字段则 N/A周期
节点健康度 health最近 1 次 passed → green；最近 1 次 failed → red；近 3 次既 pass 又 fail → flaky；无运行 → untested；指纹变化未跑 → stale只看运行结果，不含缺陷条件；枚举仅此五值，不使用 healthy节点维度

边界规则

  • 无数据 → 显示 N/A，不显示 0%；0/0 不得算 100%。
  • 运行被人工终止 → 不计入 FPR 分母；计入成本。
  • 同一 run 重试 → 以最终状态为准，重试次数写入 evidence_json.retries。
  • 跨项目产品聚合 → 先按项目聚合再求和，避免分母重复。

4.11.2 产品维度聚合规则

产品级地图不是重新扫描代码，而是项目地图的确定性 rollup，避免同一产品多项目重复分析、口径漂移。P0 只在内存中做只读 rollup 预览，不创建 map_scope='product' 版本；P1 才按以下规则落库并发布：

  1. 取该 product_key 下全部活跃项目（history_at IS NULL AND archived=0）的 active 地图（is_active=1）。
  2. 按 normalize(node_code) 合并节点：同一 code 只保留一个产品节点；各项目差异写入 test_map_nodes.variants_json（project_id / fingerprint / source_refs / health）。
  3. 节点健康度取各变体最差值（red > flaky > stale > untested > green）；覆盖率按项目节点数加权，不按项目数简单平均。
  4. 产品地图 test_maps.map_scope='product'、project_id=NULL、scope_key='product:{product_key}'、default_project_id 取产品下最近活跃项目；source_json 记录每个源项目的地图 id/版本/发布时间。
  5. 产品地图版本发布为 BEGIN IMMEDIATE 事务，遵守 §4.3.2 的 is_active 唯一约束；旧 active 版本归档。
  6. stale 触发：任一源项目地图发布新版本、项目沉淀/恢复/归档、项目彻底删除、项目 product_key 变更、项目新增/移除。产品地图下次读取时标 stale，后台重建 rollup；重建期间旧 active 版本继续可读（与项目地图「重新分析不中断当前 active」同口径）。例外：彻底删除测试资产时，含该项目变体的产品地图必须同时置 is_active=0（隔离），不得继续被读取，详见 §4.12.6。
  7. 产品下无活跃项目时：未被隔离的产品地图保留只读，节点变体全部标 missing，不允许新建草稿；已被彻底删除隔离（is_active=0）的产品地图不得读取，产品维度展示「该产品下暂无活跃项目」空态，待 P1 重建。

4.11.5 与既有模块边界

  • 任务/计划/需求/报表等既有页面不消费产品维度；顶栏切到产品维度后离开测试 group，自动回项目维度，避免「顶栏显示产品、页面数据仍是项目」的错位。

4.12.3 恢复项目（POST /history/restore / POST /history/restore-archived）

  • history/restore（历史资产 → 活跃）：清 projects.history_at；批次 state='active'、restored_at=now()；产品地图标 stale；测试菜单恢复可见。被沉淀阻塞的 run 保持 blocked 终态，不自动重跑；需要时人工重派。
  • 新增 history/restore-archived（归档 → 活跃，供归档 sheet 恢复）：清 projects.archived 与 history_at；同一事务内恢复 tasks / plan_tasks / prd_docs / prd_requirements / test_cases 的 archived=0；批次 state='active'；产品地图标 stale。项目名冲突检查与 history/restore 同口径，冲突返回 409 TEST_409_PROJECT_NAME_CONFLICT。
  • 恢复后测试地图/草稿/运行按原 id 继续可用；test_archive_batches 行保留用于审计，不删除。

4.12.4 历史快照归档删除（POST /history/to-archive）

在既有任务/计划/PRD/需求/用例软归档的同一事务内，追加：

  1. upsert test_archive_batches(state='archived', archived_at=now(), stats_json=归档时统计)。
  2. 若仍有 queued/running/optimizing 的 run（防御分支），置 blocked，error_code='PROJECT_ARCHIVED'，释放租约。
  3. 产品地图标 stale。
  4. 写审计 test.batch.archive。

测试地图、草稿、运行、证据不物理删除；仅因项目 archived=1 从测试菜单隐藏，等待归档 sheet 恢复或彻底删除。

  • snapshotted（项目仍在历史资产）→ 调 POST /history/restore，恢复整个项目；确认文案「将项目 X 恢复为活跃项目，测试地图/草稿/运行一并恢复；被沉淀时阻塞的运行不会自动重跑」。

彻底删除语义：

  • 仅允许 snapshotted / archived 批次；active 批次不在 sheet，不能删；purged 幂等返回成功。
  • 确认弹窗必须展示影响预览：地图 N 张、节点 N、草稿 N、测试任务 N、运行 N、证据 N，并明确「任务/计划/PRD/需求/手工用例不受影响；项目快照保留」。
  • 删除后批次 state='purged'，stats_json 保留删除前计数与 purged_at，供审计查询；默认列表隐藏 purged。

4.12.7 与产品维度的交集

7. UI/UX 设计建议

7.1 视觉与设计基线

  • 沿用 MTask 现有设计令牌：纯白背景、蓝色系强调色、--surface-2 分区、--border 分隔；不引入新组件库。

9.5 关键实现约束

  1. 静态事实优先：路由/导航/文件是事实来源，LLM 只补语义；禁止让 LLM 生成不存在的 route。
  2. 服务端单源：所有状态机迁移在 TestRunService / TestDraftService 内完成，前端不得自行推断状态。
  3. 不复制 Run 模型：test_runs 只做业务层聚合，步骤一律写 test_run_steps；agent_run_id 仅用于执行者/成本关联，不镜像步骤，避免双时间线。若后续要统一全局 Run 时间线，另行评估合并方案。
  4. 证据不内联 DB：只存路径/URL；图片预览走鉴权接口；禁止 base64 入库。
  5. AI 调用可中断/可续跑：分析 job 分段落盘，重试从断点继续；单次调用超时降级。
  6. 迁移零破坏：不改 tasks 结构、不改 test_cases；老库启动自动建表。
  7. 作用域单源（v1.2）：dimension / projectId / productKey 只在 TestScopeService.resolveScope() 解析一次；前端只传参数，不在组件内自行拼 scope_key；聚合态写接口由服务层二次拒绝。
  8. 归档可见性派生（v1.2）：测试数据是否可见由项目 history_at / archived 派生，禁止在 test_maps / test_runs 上再加一套 archived 标志；test_archive_batches 只存批次统计，避免双状态。
  9. 归档恢复不可拆（v1.2）：测试资产恢复必须恢复整个项目（history/restore 或 restore-archived），不提供「只恢复测试资产」的孤儿路径；彻底删除只删测试资产，不触碰任务/计划/PRD/用例。

§9.5 关键实现约束（PRD 原文）

9.5 关键实现约束

  1. 静态事实优先：路由/导航/文件是事实来源，LLM 只补语义；禁止让 LLM 生成不存在的 route。
  2. 服务端单源：所有状态机迁移在 TestRunService / TestDraftService 内完成，前端不得自行推断状态。
  3. 不复制 Run 模型：test_runs 只做业务层聚合，步骤一律写 test_run_steps；agent_run_id 仅用于执行者/成本关联，不镜像步骤，避免双时间线。若后续要统一全局 Run 时间线，另行评估合并方案。
  4. 证据不内联 DB：只存路径/URL；图片预览走鉴权接口；禁止 base64 入库。
  5. AI 调用可中断/可续跑：分析 job 分段落盘，重试从断点继续；单次调用超时降级。
  6. 迁移零破坏：不改 tasks 结构、不改 test_cases；老库启动自动建表。
