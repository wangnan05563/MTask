## 3. 本轮优化

### 3.1 任务行 `content-visibility` 样式缺失（实际瓶颈）

- 现象：`TasksPage` 给 `li.task-item` 挂了 `cv-auto` 类，但 `.cv-auto` 样式只写在设置页（`settings.tsx`），任务页从未加载该样式；5k 列表滚动基线 **54.6fps**（p95 33.3ms，3 个长帧）。
- 修复：在 `TasksPage` 页内样式补 `.cv-auto { content-visibility:auto; contain-intrinsic-size:auto 40px; }`，让屏外行跳过渲染。零业务行为变化。
- 效果：5k 列表 **54.6 → 59.6/60.0fps**，长帧 3 → 0。
- 说明：`TASK_OVERSCAN` 保持 4、`TASK_WINDOW_STEP` 保持 2，未改动窗口数学与触底续取；曾试验 overscan=2，帧率反而降到 49.2fps，已回退。

### 3.2 Windows 换行导致 T03215 门误红

- 现象：`verify-t03215` 的 S-04 正则按 `\n` 写死，Git 工作区 CRLF 下 `const nearEnd = count > 0\r\n` 匹配失败，门报「行为失守」。
- 修复：读取 `TasksPage.tsx` / `taskListWindow.ts` 源码后统一 `.replace(/\r\n/g, '\n')`，只影响测试读取口径，不碰产品代码。
- 回归：T03215 门 **32/32 PASS**。

## 5. 边界与遗留

- headless Chrome + SwiftShader，未覆盖真实 GPU、移动端、120Hz 屏；真机数值可能更高。
- 看板 5k 全量仍渲染 5000 个 DOM 节点（本次滚动达标但首次切换 ~1.07s）；更大规模（1 万+）建议后续做看板列虚拟化。
- 列表 5k 滚动达标依赖 `content-visibility`（Chromium 桌面壳支持）；非 Chromium 环境无此优化，需另测。
- 性能报告只覆盖任务页列表/看板与任务搜索，不含日历、表格、全局搜索与后端导出等路径。

## 8. 2026-11-26 收口（窗口下沉 + 行距修正 + 滚动期 tooltip）

### 8.1 代码改动

1. **窗口状态下沉到列表子树**（`TasksPage.tsx`）：`useTaskListWindow` 从 `TasksPage` 顶层移入模块级 `TaskListWindow`，列表滚动只重渲染列表自身；父层定位通过 `taskListRef.revealIndex` + 低频 `listRevealNonce` 回传。滚动期间父页渲染 0 次。
2. **行元素缓存**：`rowCacheRef` 以 `renderItem` 引用为版本键，滚动换窗只调用新进入窗口的 `renderTaskItem`，旧行复用同一 ReactNode；缓存上限 160。
3. **行距测量修正（本轮真正的波动根因）**：原实现用 `li.offsetHeight` 直接累计，两个错误叠加——① `content-visibility:auto` 的屏外行返回 `contain-intrinsic-size`（`auto` 还会记住上次可见高度），样本混入 44/78px 假值；② `offsetHeight` 不含 `margin: 6px 0`，按它当行距会让 5000 行总高每行少算约 6px，窗口切得偏大。
   现在只取「完整落在视口内、且非 hover/编辑/抽屉」的相邻两行 `rect.top` 差值作为行距，累计到 600 个样本后停止逐窗测量。5k 占位总高由错误的 185,490px（≈37px/行）修正为 220,248px（≈44px/行），窗口行数从 35~40 收敛到 31 行，帧率同时稳定。
4. **滚动期禁用 hover 工具栏展开**：`ul[data-task-scrolling="1"]` 下把 `.task-toolbar` 的 `max-height:0` 覆盖回来，避免指针随窗口落到不同行时反复触发 `0→96px` 布局。
5. **窗口常量定为 4/4**：`TASK_OVERSCAN=4`、`TASK_WINDOW_STEP=4`；22 行窗口在 420px/70ms 的快速滚动下每拍换窗，单帧成本压进预算。
