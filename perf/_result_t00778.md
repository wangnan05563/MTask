# T00778 处理结果：向量语义检索（按需触发）——触发条件评估，结论为「不立项」

## 一、结论

**本轮不实施，建议关单或转入「搁置」观察。**

T00778 的任务描述本身写明了明确的**触发条件**：

> 触发条件（满足其一才立项）：单项目源文件 > 2000，或 P0 关键词搜索召回率明显不足。

### 条件 ②：P0 关键词搜索召回率明显不足

**无证据支持**，且恰相反：

1. P0 关键词检索刚在 **T00786 / T00777** 完成性能治理（扫描预算 + memo 缓存 + 检索增强注入预算），
   2026-09-18 全端点压测中 `GET /api/workspace/search` 最坏情形（无命中）p50 139ms，
   已归入 F4 并有明确优化结论——**是性能问题，不是召回率问题**；
2. 全项目 268 条已完成任务中，**无任何一条记录关键词检索召回归因的缺陷**；
3. T00772 评估报告原文（`docs/T00772-工作空间文件搜索评估.md:15`）：

   > P0/P1 即可支撑当前 AI 控制台卡片的代码分析场景，**P2 在项目规模超过千文件前不必要**。

   当前 184 文件，距「千文件」尚有 5 倍余量。

| 项 | 值 |

| 判定依据 | 无召回率不足的实测/用户反馈；既有结论为「千文件前不必要」 |

## 三、为何不做（成本收益）

即便强行实施，当前也**收益近零、成本不低**：

| 维度 | 说明 |
|---|---|
| 收益 | 184 文件的规模下，关键词检索 + 按需读文件（P0/P1 已落地）已足够支撑代码分析场景；向量检索的召回优势在千级文件以下无法体现 |
| 成本 | 引入 embedding（本地 bge-m3 或 API）+ 向量库（sqlite-vec/LanceDB）+ 分块策略 + 索引生命周期管理，**运维与依赖复杂度显著上升** |
| 参照 | T00772 报告已指出：**WorkBuddy 自身也默认关闭向量索引**，采用「关键词默认可用、向量按需开启」的分级策略 |
| 任务自身定位 | priority = `low`，且描述写明「明确不做：完整 LSP 集成、云端全量代码上传索引」——本就是一个「等信号再动」的储备项 |
