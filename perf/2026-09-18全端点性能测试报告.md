
## 3. 关键发现（F1-F8）

**F1（P0）需求矩阵反查是 O(N×M) 且随数据二次方恶化。**
`PlanService.listRequirements()`（`server/src/services/PlanService.ts:1456`）对每条需求 `plans.filter(p => parse(p.req_ids).includes(rid))`、`tasks.filter(...)`——每条需求都把全部计划（40）与全部任务（300+）的 `req_ids` **重新 JSON.parse 一遍**。实测：
- 种子数据（400 需求 × 340 计划/任务）：每次调用 ≈13.6 万次 parse，p50 20ms；
- 经 8 分钟写负载膨胀后（≈1350 需求 × ≈2200 计划/任务）：≈300 万次 parse/次调用，p50 **474ms、p95 949ms**——数据量 ×3.4/×6.5，延迟 ×24，符合二次方曲线。
修复代价极小（一次性反向索引，见 §4 P0-1），预期收益 >95%。

**F2（P1）SQLite 写吞吐随并发反降 + 每语句 autocommit。**
写负载 5→10→20 并发吞吐 533→454→372 req/s。两个叠加因素：① SQLite 单写者串行；② 服务端多数写路径逐语句 `prepare().run()`（better-sqlite3 自动提交 = 每条语句一个独立事务 + fsync）。`connection.ts` 已开 WAL 但未设 `synchronous=NORMAL`（默认 FULL，每 commit 强制 fsync）。

**F2'（P0，写路径特例）`refreshSymbols` 无事务包裹。**
`WorkspaceService.refreshSymbols()` 对每个符号逐条 `DELETE`+`INSERT`（每条都是独立 autocommit 事务）。600 文件冷建索引实测 1655ms；若工作空间更大（真实项目数千符号），会以秒级阻塞事件循环。包一层 `db.transaction()` 即可数量级改善。

**F3（结论性）读路径存在明确的事件循环饱和点 ≈570 req/s。**
better-sqlite3 是同步 API + Node 单线程：15 并发已达峰值（574），30 并发吞吐不再增长、p50 翻倍（25→50ms）、`/health` 等空端点也被抬到 p50 50ms。**对桌面单用户场景该容量余量充足（≥50 倍于真实交互流量），不构成缺陷**；但若未来多人共用隧道部署，这是架构上限（见 §4 P2-6 说明）。

**F4（P1）workspace 全文检索最坏情形无界。**
`WorkspaceService.search()` 无命中时必须同步读完整个工作空间（逐文件 `readFileSync` ≤1MB + 全文 `includes`），600 文件夹实测 139-567ms/次；真实大仓库（数万文件）会把事件循环卡死数秒。已有 50 条命中早退，但「无命中/弱命中」路径无任何截断。

**F5（P2）导出/报表端点单次成本高但已有 worker 隔离。**
`plans/export` 283ms（同步主线程）；`report/generate` 165-216ms（xlsx/pdf 走 worker，CPU 峰值 166% 证明多核生效，且前轮已验证空闲回收）。剩余风险是**无并发上限**——多人同时点导出会叠加。

**F6（P2）`/api/history/list` 是 N+1 全量快照。**
每快照项目两次全列查询（含 description 全文）+ JSON 全量下发。当前数据（6 快照 × 60 任务）p50 9.6ms 无碍；快照量增长后线性劣化，且响应体可能数 MB。

**F7（P2）冷启动首个请求 ≈1s。**
轮 1 探针显示进程启动后首个到达的请求耗时 ≈1073ms（JIT/惰性初始化），之后同端点 <10ms。Electron 主进程有健康探针重试，无用户可感影响；如需消除可加启动自预热。

**F8（正确性）高并发未暴露竞态 bug。**
16.4 万样本、写负载含并发 create/patch/reorder/batch，0 错误 0 缺陷；唯一约束（项目名全局唯一含历史快照）在探针中行为正确。`linkRequirement` 的 const 重赋值 bug 属编译期拦截（§5），与并发无关。

## 4. 优化建议（按优先级，含预期收益）

### P0-1｜`listRequirements` 反查建一次反向索引（改动 ≈15 行）
**做法**：进入函数先遍历一次 plans/tasks，把每行的 `req_ids` **只 parse 一次**，构建 `Map<reqId, {plans:[], tasks:[]}>`，再按需求查表；复杂度 O(N×M) → O(N+M)。
**预期收益**：stability 规模数据下该端点 p50 **474ms → <15ms（≈-97%）**；更重要的是解除全服务事件循环阻塞——stability 阶段 `/health` p50 309ms → 预期 <20ms，全接口 p95 恢复到 reads_mid 水平（≈45ms）。
**验证方式**：复测 `stability` 阶段，对比 `prd_reqs_list` p50/p95 与慢日志累计阻塞时间。

### P0-2｜`refreshSymbols` 全程包 `db.transaction(() => {...})`
**做法**：把 walk 内所有 DELETE/INSERT 收进单个事务（better-sqlite3 同步事务零成本）；顺带把「每文件 SELECT MAX(mtime)」改为启动时一次性载入 `(path→mtime)` Map。
**预期收益**：冷建索引 1655ms → **<300ms（≈-80%）**；大仓库从「秒级卡顿」降为「百毫秒级」；同时消除逐条 fsync 的磁盘写放大。

### P1-1｜WAL 模式下设 `PRAGMA synchronous = NORMAL`
**做法**：`connection.ts` 在 WAL 打开成功后追加一条 pragma（约 1 行）。代价：断电可能丢失最近若干事务（WAL 保证不损坏库）；对桌面单机应用是合理取舍。
**预期收益**：写路径每次 commit 免一次 fsync，写吞吐预期 **+30%~60%**（writes_stress 372 → ≈500+ req/s），`add_holiday` 等 p95 139ms → ≈60ms。

### P1-2｜`console-jobs` 列表加 TTL 缓存或分页
**做法**：GET `/api/console-jobs` 现为无缓存全表 `SELECT *`（含完整 answer 长文本），前端轮询调用。仿照 `projects` 的 5s TTL 缓存（`LIST_TTL_MS` 模式已有现成基建），或 `LIMIT 50 + since 游标`。
**预期收益**：轮询场景 DB 行读与 JSON 序列化 ≈0；该端点在混合负载下 p50 310ms → <30ms（其中大头本为排队，缓存消掉自身 DB 成本后排队源进一步减少）。

### P1-3｜workspace 搜索最坏情形治理
**做法**（任选其一或组合）：① 无命中路径也设「已扫描文件数上限」（如 2000 个即停，返回 partial 标记）；② 维护 mtime 增量文件清单缓存（复用 refreshSymbols 的扫描结果）；③ 搜索移入 worker_threads。⚠️ 若移 worker，注意 better-sqlite3 实例不可跨线程，需在工作线程内独立打开只读连接或纯 FS 扫描。
**预期收益**：最坏情形 139-567ms → **<20ms**，且彻底消除大仓库下的事件循环长阻塞风险。

### P2-1｜`history/list` 消 N+1
一次 JOIN/`IN` 查询 + 内存分组替代每快照两次全列查询；`tasks` 查询去掉 `description` 大字段（列表页不需要）。预期快照 ×10 增长后仍保持 <30ms。

### P2-2｜导出端点并发闸
`plans/export`、`settings/export`、`dbadmin/*/export` 加简单的进行中计数信号量（如同时 2 个），超出返回 429/排队提示；报表已有 worker 隔离，可保持现状。

### P2-3｜任务列表 keyword 检索
`title/description LIKE '%kw%'` 双列全表扫（当前 2500 任务 p50 无感）。数据过万或移动端高频搜索时再考虑 FTS5 虚表；现阶段仅建议给 description 检索加长度前置截断。

### P2-4｜语句级 prepare 复用
热点路径每次 `db.prepare(sql)`（TaskService.list 动态拼 SQL）。对稳定 SQL（list 各排序变体、update、insert）按 SQL 串做 Map 缓存。预期单项收益 3-8%，攒够一批再做。

### P2-5｜（流程）AI 端点本地编排成本评估
用 `server/scripts/mock-ai-server.mjs` 把 26 条外部依赖端点的上游 mock 后单测其本地开销（prompt 组装、上下文注入、PRD 上下文截断），验证 `prdContext`/`autoContext` 预算控制是否生效。

### P2-6｜（部署形态说明，负载均衡）
本后端为 Electron 本地单实例 + 同步 SQLite 架构，**不适用横向负载均衡**；若未来改为团队共享部署：读扩展可用 node cluster + 每进程独立只读连接，写扩展必须换网络库（PostgreSQL/MySQL），不建议对 better-sqlite3 做多进程写。隧道场景（cloudflared）下当前单实例 ≈570 req/s 上限对中小团队（<50 人）依然充裕。

### 建议实施顺序
```
P0-1（15 行，立刻）→ P0-2（10 行，立刻）→ 复测 stability 验证
→ P1-1（1 行，随下个版本）→ P1-2 / P1-3（按迭代排期）
→ P2 按数据增长触发（当前规模均不紧迫）
```
