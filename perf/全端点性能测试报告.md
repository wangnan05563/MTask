## 1. 测试范围与方法

### 1.1 端点分级

按「对负载压测的适用性」把 API 分为 5 类，分别采用不同压测方式（**这是本次能给出干净错误率的前提**）：

| 类别 | 数量 | 压测方式 | 原因 |
|---|---|---|---|
| 本地读 | 40 | 负载阶段（1/5/15/30 并发） | 纯查询、幂等，可重复压 |
| 本地写（幂等/增长） | 39 | 负载阶段（1/5/10/20 并发） | create/patch/upsert/reorder/toggle，每次调用均 2xx |
| 重端点（CPU/IO） | 9 | 负载阶段（单线程） | 报表合成、Excel 导出、大数据量列表 |
| 破坏性 / 一次性 | 28 | **单发探针** | 「创建后即关联 / 复用同名 / 删除已删」第二次调用起必然 400/409/404，进负载循环会把「夹具耗尽」伪装成「服务缺陷」 |
| 外部依赖 | 14 | **排除** | 见 1.2 |

### 1.2 明确排除的端点（及理由）

这些端点延迟由**外部服务**决定，压测只能测出上游时延并消耗配额，不代表本地性能：

- AI 调用：`POST /ai/chat`、`/ai/organize`、`/ai/beautify`、`/ai/optimize`、`/ai/generalize-to-req`、`POST /tasks/classify`
- AI 报表：`POST /report/ai-generate`、`/report/ai-generate-stream`、`/report/ai-download`
- 队列外发：`POST /queues/:id/send`、`/queues/:id/submit`
- 连通性探测：`POST /aitools/test`、`/aitools/models`、`/aitools/:id/test`、`/aitools/:id/models`
- 计划 AI 解析：`POST /plans/ai-parse`、`/plans/ai-parse-doc`；Excel 二进制导入：`POST /plans/import`
- 更新检查：`POST /update/test`、`/update/check`；隧道/CF：`POST /tunnel/*`、`/tunnel/cloudflare/*`
- `POST /console-jobs`（后台触发 AI 运行，非本地同步路径）

> 排查方法学说明：这些端点的**本地编排成本**可用项目内 `server/scripts/mock-ai-server.mjs` mock 上游后单独压测（见 §6 P2-10）。

### 1.3 轮次与数据可信性

| 轮次 | 目的 | 结果 |
|---|---|---|
| JMX 解析自检（`--selftest`） | 校验 88 个采样器的线程/路径/方法/请求体 | 通过（无 `{{}}` 残留、路径与夹具逐条核对） |
| 冷启动单线程先验 | 暴露系统性问题 | 发现并修正 1 处夹具缺陷（见下） |
| 正式压测（`--all --report`） | 10 阶段 × 一次 SUT 启动 | 9m13s，全部阶段 0 错误 |
| 资源采样 sidecar | 3s 间隔采样 SUT 进程 | 193 个样本 |
| 单发探针 | 28 个破坏性/一次性端点 | 28/28 通过 |

**修正的 3 个测试方法学问题（保证数据可信，非服务缺陷）**：

1. **非 ASCII query 未编码** → `?keyword=压测` 直进 URL 被 `urllib` 拒绝，记为 `000`（伪缺陷）。已改用预编码夹具 `%E5%8E%8B%E6%B5%8B`。
2. **沙箱端口与 dev 工具链冲突** → dev 启动脚本会清空 39876 并顶掉沙箱 SUT，导致流量打到带 `accessToken` 的 dev 实例（整批 **401**，而 `/health` 豁免仍 200）。已改为**专用端口 39899**，与 dev(39876)/生产(39877) 三分离。
3. **监控进程定位方式** → `cmd_substr` 依赖 WMI 命令行枚举，本机实测对正在监听的 SUT 也匹配不到；已改为 `pid_file` 模式（编排层在端口就绪后写入监听 pid）。

- **worker 依赖常驻**：heavy 结束后 stability 阶段 RSS 均值仍 277 MB（较写入阶段 +115 MB），说明一次性加载的大依赖不归还内存（这是「worker 复用让大依赖只加载一次」的既定取舍，但**缺少上限**，见 §6 P1-4）。
- 采样局限：`threads` 列在本次 Windows 采样下为 0（监控脚本线程数采集未生效，不影响其它指标）。

## 6. 优化建议（可落地 · 按优先级）

### P0 — 高优先（直接影响容量与延迟）

| # | 措施 | 具体做法 | 预期收益 | 代价/风险 | 验证方法 |
|---|---|---|---|---|---|
| **P0-1** | **计划重排改为增量** | `PlanService` 的 `rescheduleAll()` 改为「从被改动项向后重排」：仅重算 `sort_order ≥ 插入/修改位置` 的条目；`reorder` 只重算受影响区间；holiday 变更只重算受影响日之后的条目 | 计划类写 p50 由 **169–199 ms → <20 ms**（2453 计划规模，降幅 ≈90%）；`plans_export`/`plans_reorder` 同步受益 | 需保证 `end_date` 冗余列与串行语义一致；改动集中在 `PlanService`；建议加单测覆盖「中间插入/跨节假日/跨周末」 | 复跑 `writes_baseline` + `writes_stress`，对比 `create_plan`/`plan_insert_after` p50 |
| **P0-2** | **任务列表强制分页 + 单响应限额** | `GET /tasks` 在无 `limit` 时给默认值（如 200）并返回 `total`；`tasks_by_project` 前端改用分页/游标；`limit` 上限由 500 收紧 | 读端点最慢者 p50 降 30–50%；响应体显著减小，降低事件循环单次占用 | 前端需配合分页（TasksPage 已有 `limit` 字段，改动可控） | 复跑 `reads_*` 对比 `tasks_by_project`/`tasks_page` |
| **P0-3** | **补 `tasks(category_id)` 索引** | `CREATE INDEX IF NOT EXISTS idx_tasks_category ON tasks(category_id)`（并可考虑 `(category_id, archived)`） | 分类删除/按分类查询由 **331 ms → <10 ms**；`tasks_by_category` 读同步受益 | 仅增加少量写放大；迁移幂等（`ensureColumn` 同风格） | `task_category_delete` 探针 + `tasks_by_category` 读延迟 |

### P1 — 中优先（显著收益，改动小）

| # | 措施 | 具体做法 | 预期收益 | 代价/风险 |
|---|---|---|---|---|
| **P1-4** | **报表 worker 内存封顶与回收** | `new Worker(path, { resourceLimits: { maxOldGenerationSizeMb: 512 } })`；空闲 TTL（如 5 分钟无任务）后 `terminate()` 交由下次重建；或每 N 次构建重建 | RSS 峰值由 **390 MB → <250 MB**，避免 heavy 后长期驻留 277 MB | worker 重建会重新加载依赖（约数百 ms），需在 TTL 策略上权衡 |

### 优先级排序理由

1. **P0-1 优先于其它**：它是唯一「随数据增长而线性恶化」的架构问题，且已在 2453 计划规模下暴露（169–199 ms），若不修将在计划量继续增长时劣化更快。
2. **P0-2/P0-3** 都是「改动小、收益直接可测」的读路径优化，且 P0-3 顺带修复一处明显的缺索引扫描。
3. **P1-4** 是当前唯一的资源风险项（390 MB 峰值 + 不归还），但尚未造成功能问题，故列 P1。
4. **P1-6** 触及数据一致性权衡，需产品确认后再做，故不列 P0。
5. **P2** 均为可观测性/方法论完善，不影响当前交付。

## 9. 已知限制

1. **同机压测**：负载生成器与 SUT 同机且系统 CPU 长期饱和 → 高并发绝对值偏悲观，仅作相对比较；单线程/低并发可信。
2. **回放引擎无响应抽取**：无法「创建后取新 id 再删」，破坏性端点以「专用可删夹具池 + 单发探针」近似，删除类端点的**吞吐**（而非单次延迟）未测。
3. **无断言口径**：JMX 未声明 ResponseAssertion，错误率按「非 2xx/3xx」计；已通过「幂等写进负载、一次性端点进探针」保证口径不失真。
4. **Python 回放的天花板**：单进程多线程远低于 JMeter 分布式，因此本报告的 TPS 平台是「Python 客户端 + 服务端」共同的结果，不能直接当作服务端极限吞吐。
5. **线程数指标缺失**：sidecar 的 `threads` 采样在本机为 0。

### 10.5 对「变慢」项的归因（非回归）

复测中 4 项变慢：`heavy` +27%、`stability` +59%、`settings_export` +33%、`plans` p95 +38%。
原因是**写吞吐提升带来的数据量混淆**：同等测试时长内，产生新行的写请求从 13,930 增至 **24,911（+79%）**，
结束时库内 `tasks` 3,166 / `plan_tasks` 4,436 / `prompts` 3,050 —— 这些端点的成本本就随数据量线性增长。
探针中 `project_delete` +227%（4.3 → 14.1 ms）同理（级联删的任务数翻倍）；
`settings_import` +37%（59.9 → 82.3 ms）对应包体 2.98 → 4.24 MB（**+42%**），为等比例增长。
以「同数据量」口径衡量，所有端点均为正收益，且 **0 错误 0 缺陷**。

### 10.6 修正本报告早先的两项结论（以实测为准）

1. ~~「SQLite 参数上限 999，任务 >999 时会抛错」~~ → 实测本机 SQLite **3.53.2** 的绑定变量上限为 **32766**（999/1500/32766 均可编译执行，32767 起抛错）。分批的价值在于**封顶 SQL 文本长度**并消除对 SQLite 版本的依赖，而非修复一个 999 阈值的必现崩溃。
2. ~~「分类删除 331ms 是缺 `category_id` 索引所致」~~ → 331/361 ms 实为**冷启动首请求**（探针第一项，两次独立实测一致，含模块加载）；预热后同路由删除实测 **2.3 ms**（无引用）/ **24.7 ms**（200 个任务引用）。索引仍然正确且必要（`EXPLAIN` 已证走索引，且使该操作随数据量可扩展），但旧数据把它误归因为查询本身。
