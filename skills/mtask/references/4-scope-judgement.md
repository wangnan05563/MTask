# Reference 4 —— 归属/可落地判定与询问规则

在批量处理待办前，必须先做「归属」与「可落地」两层判定，避免在错误项目里硬改代码、或对无法闭环的任务假装修好。

## 一、归属判定（是否当前项目）

判断依据：任务字段 `project_id`。

```text
project_id  == 当前工作区项目 id  → 本环境处理
project_id  != 当前项目           → 跨项目，标记「本环境不可落地」
project_id  未知/缺失              → 按 title/description 内容人工判断归属
```

要点：
- mtask 的清单跨多项目时，混合的待办看起来都在同一张表里，**必须先按 project_id 分桶**。
- 不要凭 title 进入；title 相似的「知识问答」可能属于不同仓库。

## 二、可落地判定（能否真正执行）

| 类型 | 特征 | 处置 |
|---|---|---|
| A 真修复 | 当前工作区有代码/接口/脚本可读可改、可自检 | 实际修改 + 自检 + 回传 |
| B 仅评估 | description 是通用模板、未指明服务/文件；或强依赖外部系统 | 输出结构化评估/说明，请求补充上下文；不做伪修复 |
| C 外部环境 | 需专人测试、外部目录、另一台机器、实时数据 | 标注依赖项，本会话不闭环，不置 done |

## 三、何时必须询问（AskUserQuestion）

下列情况**不要默默选一种解释就开始**，用 AskUserQuestion 让用户拍板：

1. **处理范围不清**：清单多处跨项目，或用户只说「处理待办」未指明只处理本项目。
   - 选项示例：仅当前项目几条 / 全部打评估 / 逐条确认 / 只处理某条。
2. **任务描述模板化、目标对象不明**：比如「评估 XX 服务」，但没说是哪个服务——先问清楚评估对象，再决定评估深度。
3. **涉及改动会影响生产/共享配置**：先列出约束（如「不得修改 AI 服务实际配置」），确认修复边界。

## 四、范围缺省值

用户未特别说明时，默认策略：
- 只处理 `project_id == 当前项目` 的待办；
- 其余跨项目待办保持 `todo` 不动，在最终汇报中列明；
- 处理顺序 = `task_no` 升序。

## 五、诚实边界（防过度承诺）

- 跨项目任务：绝不尝试在错误仓库里「硬改」实现效果。
- 无法验证的修复：文档标注「需在 XX 环境实测」，不伪装已验证。
- 无上下文的任务：回传时说明缺什么信息，把球交还给用户补充，而不是编造输入继续往下推。
