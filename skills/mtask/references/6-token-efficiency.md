# Token 效率优化方案（mtask 待办批量处理场景）

> 依据 2026-09-13 实测轮（T00465-478，14 条任务约 60+ 工具调用）复盘提炼。
> 原则：**不降低功能完整性、不影响结论准确性与专业性、不损害交互体验**——只砍"过程噪音"，不砍"结论密度"。
> 所有阈值/开关集中在 `config/config.yaml` 的 `token-efficiency` 节，无硬编码。

## 一、四类措施与实施要点

### 1. 对话上下文管理（截断与保留）
| 措施 | 做法 | 预期节省 |
|---|---|---|
| 详情分批读取 | 任务详情按 `detail-read-batch-size`（默认 7）分批拉，单条截 `detail-read-char-limit`（默认 500 字符）；超长 description 只在需要时二次取全 | ~15%（详情读取占轮次 Token 大头） |
| 结果不重读 | 已回传过 handle_result 的任务，其详情首轮已入上下文，后续清单/关联分析直接复用，禁止再次 `get_task` | ~8% |
| 查询收窄 | 永不全量拉取：已定位项目用 `mtask_list_tasks({projectName})` 服务端过滤；需要状态维度时显式传 `status` | 首轮清单 ~50-90%（全量数百条 → 单项目十几条） |
| 大结果按需提取 | 工具结果 >2000 字符时，后续引用改 grep/sed 按需提取字段，不整段回显 | ~10%（视结果体量） |

### 2. 输入内容预处理
| 措施 | 做法 | 预期节省 |
|---|---|---|
| 描述去模板噪音 | 任务 description 常含「## 目标/输入/约束/步骤/期望输出」模板框架，读取时先剥离重复框架词、保留业务语义行，再进入分析 | ~20%（模板化描述占比高时） |
| 查询格式标准化 | 用户指令统一解析为 `{项目名?, 范围?, 单条?}` 三元组，缺省走 config 缺省值，不反复澄清（范围歧义仅一种情况需问：跨项目且未点名） | 减少一整轮澄清对话（~1 轮 = 5-15%） |
| 错误快速判型 | 工具报错先按 config 的已知症状表（list-tools-failed / 401 / 端口占用）判型直取处置，不重试-观察-再猜的多轮试探 | 失败场景 ~30% |

### 3. 响应内容优化
| 措施 | 做法 | 预期节省 |
|---|---|---|
| result 精简版缺省 | 回传默认三节「根因/修复/验证」（`result-lite-by-default`），「影响范围」仅跨模块改动时补；上限 `result-max-chars`（默认 1200 字符），超限先砍背景/过程，保结论密度 | 单条回传 ~25-40% |
| 表格化汇总 | 最终汇报用单张表（任务/内容/落地/commit/验证状态），不逐条段落铺陈 | 汇报段 ~40% |
| 验证证据一行化 | 冒烟/构建证据压成一行（`tsc ✅ build ✅ API:400✅`），不贴完整输出；仅失败时贴关键报错行 | ~10% |
| 禁复述 | 回传与汇报不重复任务原文描述，只写增量结论 | ~5-10% |

### 4. 交互流程合并
| 措施 | 做法 | 预期节省 |
|---|---|---|
| 单轮闭环 | 逐条「改→验→commit→回传」在同一轮工具序列内完成，不拆多轮等待 | 轮次数 ~50%（轮次开销是大头） |
| 批量冒烟合并 | 同类改动（如 4 页 reveal）构建一次覆盖全部，不每页各跑一次 tsc+build | ~10-15% |
| 分组提交 | `commit-per-task: false` 时按分组合并 commit（如 T00476/77 一条 commit），commit message 合并写两任务 | ~5% |
| 一次清单多任务复用 | 首轮 pending 查询结果作为全程决策底册，不反复重查（处理中新增的任务由完成标注后的一次复查覆盖） | ~5% |

## 二、综合节省估算（基于本轮实测外推）

| 场景 | 本轮实测基线 | 预期节省 |
|---|---|---|
| 单条简单任务（UI 小改） | 详情 0.5k + 改验 3-5 调用 + 回传 1k 字符 | **~25%**（精简回传 + 一行证据） |
| 批量同构任务（如 6 条 UI） | 公共设施 + 合并冒烟 | **~35-45%**（合并构建 + 表格汇报 + result 精简叠加） |
| bug 排查类 | 读代码 + 隔离复现（复现链路本身就贵） | **~10-15%**（仅回传与引用环节可省；复现不可省——准确性优先） |
| 首轮清单获取 | 全量 vs 按项目收窄 | **~50-90%**（最大单项收益） |

> 估算口径：Token ≈ 输入上下文（任务详情+工具结果回显）+ 输出（回传文档+汇报）。上表为各措施独立叠加的区间估计，实际受任务模板化程度与失败率影响；**准确性相关支出（bug 复现、根因证据）不参与压缩**。

## 三、验证方法（方案有效性可测）

1. **A/B 对照**：同一批已知任务（或同规模构造任务集），分别按「旧流程（全量拉取+逐条完整回传+每页单独构建）」与「新流程（config 开关全开）」各跑一轮，对比总 Token 消耗（会话级 usage 统计）与完成质量（verified 判定准确率、回传信息完整度抽检）。
2. **质量护栏断言**：
   - 回传抽检：每条 result 必含「根因/修复/验证」三节且验证节有可复现证据（命令+结果），缺失即判不合格——防止精简变偷工。
   - 假绿抽检：对 UI 类任务的 dist 产物 grep 特征串，与处理结果声明一致。
   - verified 判定抽检：人工复核 verified=1 的任务是否真的命令层闭环（对照 T00478 规则）。
3. **回归指标**：节省比例达成 ≥20%（简单批量场景 ≥35%）且质量护栏零违例，则方案有效；未达标则回滚对应 config 开关（开关粒度=每措施独立，可单独关闭定位劣化源）。

## 四、不适用边界

- **bug 根因复现链路不压缩**：隔离复现、端口归属核查、双库比对等准确性支出优先于 Token 效率。
- **用户明确要详细过程时**：以用户要求为准（config 开关覆盖为手动模式）。
- **低频复杂任务（单条重型排查）**：合并类措施收益趋近零，仅保留回传精简与查询收窄。
