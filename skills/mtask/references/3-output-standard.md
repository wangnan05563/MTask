# Reference 3 —— 输出标准（回传文档 + 完成标注）

本文件是「结论文档」与「完成标注」的质量基线，处理每条任务回传前必须对照。

## 一、回传 `result` 文档结构（Markdown）

`mtask_update_task_result({ taskNo, result })` 的 `result` 必须结构化为以下四段（最少前两段）：

```markdown
## 根因
一句话定位 + 根本原因陈述（避免只复述现象）。可含：哪个文件/哪一侧（前端/后端/配置）、
为什么会出现（触发条件/数据流）。若多因，分点列出并指出主因。

## 影响范围
受影响的页面/接口/用户/功能；是否涉及生产配置；是否影响其它模块。

## 修复
逐点说明改动，尽量带文件绝对路径与改动点（类/函数/Vue 行号）；
说明改动的「为什么」（设计取舍、安全性考量）而非仅「改了什么」。

## 验证
- 自检：按 config.yaml 的 validation.static-check-commands 运行，0 错误、退出码、单测结果。
- 运行实测（如有）：把可观测证据写进来——UI 弹出的确切文案、HTTP 状态码、
  返回体原文、控制台日志等。
- 明确区分「已实测」与「仅静态/无法在本机验证」，不把推测当结果。
```

## 二、硬性质量要求

1. **诚实边界**：不做伪修复、不伪造验证。无法验证就写「需在 XX 环境实测」。
2. **可复核**：修复点必须能让人按文档定位到文件；验证必须有命令/证据。
3. **不泄漏**：结论文档不发生产密钥、内部 token、脱敏后的真实账号密码等敏感信息；
  要用占位符（如 `<token>`、`admin/123` 仅作示例说明）。
4. **不擅改配置**：若任务是展示类同步问题，优先修展示层，不擅动 AI 服务真实配置。

## 三、完成标注标准

只有「已回传结构化解结论 + 至少完成静态自检（+ 尽可能的运行验证）」才标注完成。

- `mtask_update_task({ taskNo, status: 'done', verified: true })`
- 未达上述标准 → 保持 `status='todo'`、`verified=false`，并在汇报中说明卡点。

## 三b、「下一步建议」节建单化（T01547，2026-10-07 口径反转）

result 末尾可附 `## 下一步建议（可选）` 节（1~3 条，动词开头；无建议整节省略，不注空值）。
该节**不是「不建单」的出口**——凡条目包含需要再执行的动作，必须为其建派生子任务：

1. 建单口径与 `config.writeback` 完全一致：`【AI回写待审核】` 标题前缀 + `derivedFrom={原任务编号}` +
   必带 projectName/projectId + 建单前查归档防重复 + 新单置 unread；
2. 建单后在该建议行末尾标注编号：`- 建议内容 —— 已建派生单 Txxxx`，编号同步列入「本次回写」节（两处同一本账、可互查）；
3. 仅无需再派活的纯观察提示（风险备忘、请用户留意的一句话）允许留在文本，
   但必须显式行末标注 `（仅观察不建单）`——防止动作项借「建议」之名漏网；
4. 需用户先决策的动作照常建单（待审核前缀本身就承载准入语义）。

判断口诀：**有建议必有单；纯观察才标注**。

## 四、示例（脱敏）

```markdown
## 根因
问答页把「问答失败」提示映射为全部 HTTP 400，而 400 实际来自后端 BYOK 校验
（未配置 API Key），前端 SSE 层又丢弃了响应体的 error 原文，导致用户看到的
是非指引性的「请求参数有误」。

## 影响范围
所有未配置 API Key 发起问答的用户；仅影响错误提示文案，不影响问答主链路。

## 修复
1. sse.ts tryFetchResponse：非 2xx 时读取响应体 error/detail 并入 Error 消息
   （原因：保留后端明确指引，避免前端二次猜测）。
2. apiError.ts：状态码后带间服务器原文时优先展示，否则回退通用映射。

## 验证
- vue-tsc --noEmit：0 错误。
- 实测：未配 Key 发送问答，前端弹出「问答失败：请先…填写 API 配置…」（与后端返回一致）。
```

（以上为示例结构，具体内容按真实任务填充与核实。）
